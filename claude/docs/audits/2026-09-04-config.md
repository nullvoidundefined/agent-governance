## Executive summary

The harness is in the best state it has been in: suites green, integrity manifest current, the judge tier honestly scoped. The findings are about the platform having moved under the config. Three things are load-bearing:

1. **P1-1**: `session-end.sh` runs under a 1.5-second `SessionEnd` budget the docs now specify, with no `timeout` set. The R-603 rollup, the fire-log rollup, and the velocity metrics are all in a hook that can be killed mid-run on any machine with a populated `projects/` tree, silently.
2. **P1-2**: the post-compaction re-injection is built on a premise the docs contradict. `SessionStart` with matcher `compact` is the documented mechanism, while a global sentinel file re-injects, one turn late, a hand-copied rule list that has drifted from `CLAUDE.md`. (Corrected same day: the memory index and handoff were never at risk, because `session-start.sh` is registered under an empty matcher and an empty matcher fires on every source, `compact` included.)
3. **P1-3**: `settings.json` starts every session on `opus[1m]` while the memory file marked HARD RULE, R-903, and the post-compaction rule list all say Sonnet is the default. The docs today price Opus 5 at 2.5x Sonnet 5, and Sonnet 5 carries a native 1M window, so the `[1m]` suffix no longer buys anything on the cheaper model.

Below them: the open P2 on secret reads has a paste-ready docs answer now (`Read(...)` deny rules that also cover `cat`, `head`, `tail`, `sed`); CI runs two actions whose pinned majors declare `node20`, which GitHub removes from runners on 2026-09-23; ESLint 9 reached end of life on 2026-08-06; and the permission mode is implicit on a plan where the built-in default became auto mode.

## P1

### P1-1: `session-end.sh` has no `timeout` and the event now carries a 1.5-second budget

`settings.json:303-311`:

```
    "SessionEnd": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "~/.claude/hooks/session-end.sh"
          }
        ]
      }
    ],
```

Docs (`hooks.md`, common fields table, and the SessionEnd section): "`SessionEnd` hooks share a 1.5-second budget; if your settings set a longer per-hook `timeout`, Claude Code raises the budget to match, up to 60 seconds" and "SessionEnd hooks have a default timeout of 1.5 seconds. This applies to session exit, `/clear`, and switching sessions via interactive `/resume`."

`hooks/session-end.sh` does, in order: `find "$PROJECTS_DIR" -type d -name memory` over every project, a nested `find` per memory dir, two `grep`+`sed` passes per memory file, a `tail`+`awk` rollup of `telemetry/rule-fires.log`, then `git rev-list`, `git diff --name-only`, and `git log --name-only` over the session range. On this checkout with an empty `projects/` tree it finishes well inside the budget; on the maintainer's machine, with `projects/` populated by every repo ever opened, nothing bounds it. A kill at 1.5 seconds loses the R-603 routing, the fire-log high-water mark advance (so the next session double-counts), and the metrics file, with no error surfaced anywhere. Governing rules: R-603, R-602, R-516 (an enforcer that can be silently killed is not an enforcer).

Direction: set a per-hook `timeout` on the `SessionEnd` entry (the docs raise the shared budget to match, capped at 60), and move the `projects/` scan behind a mtime check so an unchanged memory tree costs one `find`. To confirm: `time (echo '{}' | ~/.claude/hooks/session-end.sh)` on the real machine with the real `projects/` tree; whether `/clear` (which also fires SessionEnd) is a path the rollup should run on at all.

### P1-2: post-compaction re-injection uses a global sentinel where the docs provide a `compact` matcher, and the content it re-injects has drifted from `CLAUDE.md`

`settings.json:342-360` registers `pre-compact.sh` on `PreCompact` and `post-compact-rules.sh` on `UserPromptSubmit`. `hooks/pre-compact.sh:27`:

```
: > "$SENTINEL" 2>/dev/null || true
```

with `SENTINEL="$HOME/.claude/.post-compact-pending"`, and `hooks/post-compact-rules.sh:22-28` consumes it on the next prompt. The header comment states the premise: "PreCompact cannot inject context ... UserPromptSubmit does have one, so the work is split."

Docs, `context-window.md`, "What survives compaction":

```
| Context that hooks added earlier | Summarized with the rest of the conversation |
| SessionStart hooks that match the `compact` source | Claude Code runs them and adds their output to the compacted context |
| Project-root CLAUDE.md and unscoped rules | Re-injected from disk |
```

and `hooks-guide.md`, "Re-inject context after compaction": "Use a `SessionStart` hook with a `compact` matcher to re-inject critical context after every compaction." `hooks.md` lists the SessionStart matchers as `startup`, `resume`, `clear`, `compact`, `fork`.

Four consequences:

1. The sentinel is one file under `~/.claude` shared by every session on the machine. A compaction in session A sets it; the next prompt in session B consumes it. Session B gets the rules it did not need and session A never gets them. R-501 exists because parallel sessions are a normal condition here.
2. Withdrawn on re-check the same day. This consequence claimed the index and handoff `session-start.sh` injects were summarized away at compaction. They are not: the hook is registered under `"matcher": ""`, and the reference states "If you omit the matcher or use `"*"`, the group activates on every occurrence of the event", so it already re-runs on the `compact` source. The finding stands on consequences 1, 3, and 4.
3. The twelve rules in `post-compact-rules.sh:30-48` are a hand copy. Rule 5 ("Model routing: Sonnet default") contradicts `settings.json:104`. Rules 6 and 7 (deploy sign-off, "CSRF: X-Requested-With header pattern. No token endpoint.") are project conventions with no norm line in `CLAUDE.md` at all, injected into every project. If `~/.claude/CLAUDE.md` counts as an "unscoped" memory file for re-injection (the docs name "project-root CLAUDE.md and unscoped rules"; the user file is not named either way), the copy is redundant with a file that is already re-read from disk.
4. `post-compact-rules.sh` spawns on every `UserPromptSubmit` for the life of every session to check for a file that is almost never there.

Governing: R-001, R-002, R-204 (durable fix over symptom patch), R-501. The community report corroborates the mechanism: six GitHub issues (#4017, #16014, #16106, #17530, #19471, #24460) report CLAUDE.md content not being honored after compaction, and the converged workaround is exactly the `compact`-matched SessionStart hook.

Direction: register the rule re-injection under `SessionStart` with `"matcher": "compact"` (`session-start.sh` already covers that source through its empty matcher), delete the sentinel pair and its `UserPromptSubmit` registration, and either delete `post-compact-rules.sh` or reduce it to the rules that are not already in `CLAUDE.md` and belong globally. Update `post-compact-rules.test.sh` and `enforce/hook-hashes.txt`. To confirm: whether `~/.claude/CLAUDE.md` is re-injected after compaction (run `/compact` in a throwaway session and `/context` afterwards; the Memory files list settles it); which of the twelve rules have a `CLAUDE.md` norm line today (`claude-md-lint.test.sh` will refuse a duplicate if any are promoted).

### P1-4: secret files are still readable through file tools and recognized Bash readers, and the docs now ship the deny list

`settings.json:51-68` (`deny`) carries seventeen `Bash(...)` rules and no `Read(...)` rule. `ISSUES.md` has held the read-side gap open since 2026-07-31: "no PreToolUse guard on `Read`/`Grep`/`Glob` for R-102 secret paths; the read side is honor-system."

Docs, `settings-reference.md`, `permissions.deny`: "Use it for files that hold API keys, secrets, or environment values: Claude Code excludes matching files from file discovery and search results, denies reads of them, and blocks the Edit and Write tools on the matching paths. Read and Edit deny rules apply to Claude's built-in file tools and to file commands Claude Code recognizes in Bash, such as `cat`, `head`, `tail`, and `sed`; they don't apply to arbitrary subprocesses, so for OS-level enforcement enable the sandbox." `permissions.md`: "Bare filenames follow gitignore semantics and match at any depth, so `Read(.env)` and `Read(**/.env)` are equivalent"; `Read(//**/.env)` "any `.env` anywhere on the filesystem"; "Deny rules: apply when either the symlink path or its target matches"; "Grep and Glob search the directory the `path` argument resolves to. Claude Code applies `Read` deny rules to that directory."

This closes the R-102 read side for every path R-102 names (`.env*`, `~/.aws`, `~/.ssh`, `~/.gnupg`, gh `hosts.yml`, keychains) with zero hook code, and it removes those files from `@` mentions and search results, which no hook can do. Governing: R-102, R-103, R-516 (a rule with a native enforcer available and unused depends on recall).

Direction: add `Read(...)` deny rules for the R-102 paths, using the `//` root anchor for the dotfiles in `$HOME` and the bare-filename form for `.env*` so nested project copies match. Keep `secret-scan.sh` for the write side and for argv, which the deny does not see. To confirm: R-102's "when the user names one, use the value from memory" clause, since a `Read` deny blocks even a user-requested read of the file (the value can still reach a command through the shell's own `source`, which the deny does not intercept); that `hooks/ntfy-notify.sh` sourcing `~/.claude/.env` is a hook process, not a tool call, and is unaffected; the deny/allow interaction for `Edit` on the same paths (the docs say a `Read` deny also blocks Edit and Write there, which is R-103's intent).

### P2-1: the permission mode is implicit on a plan whose built-in default is now auto mode

`settings.json` sets no `permissions.defaultMode`. `settings.json:397`:

```
  "skipDangerousModePermissionPrompt": true,
```

Docs, `permission-modes.md`: "On Pro, Max, and Team plans, the built-in starting permission mode is auto mode"; "if your `~/.claude/settings.json` sets a `defaultMode` other than `auto` and no other settings file sets one, your sessions keep starting in that mode. Claude Code asks once ... whether to change the setting to auto mode." Auto mode: "Actions matching your allow, ask, or deny rules resolve immediately", so with `Bash` on the allow list (`settings.json:4`) every shell command bypasses the classifier and lands on this repo's hooks alone, which is the documented pattern (`permissions.md`: "To run all Bash commands without prompts except for a few you want blocked, add `"Bash"` to your allow list and register a PreToolUse hook that rejects those specific commands"). The `skipDangerousModePermissionPrompt` key exists only to silence the bypass-mode dialog, so bypass mode is in use somewhere; in bypass mode the `ask` list still prompts ("Actions no mode auto-approves ... Tools matched by an explicit ask rule") and deny still blocks ("Deny rules block in every mode, including `bypassPermissions`"). Changelog 2.1.257: `defaultMode: "bypassPermissions"` in project settings is now ignored; user settings still honor it.

What is missing is the decision. The settings do not say which mode a session starts in, so the answer changes with the plan and with the one-time prompt. Governing: R-203, the 2026-08-01 accepted-risk note in `ISSUES.md`, which reasoned about the lenient allow list under manual mode.

Direction: set `permissions.defaultMode` explicitly to the mode the accepted-risk note assumed, and append one line to the ISSUES.md accepted-risk entry stating how the lenient list behaves under that mode. To confirm: which mode the maintainer's sessions actually start in today (`/status` shows it); whether the classifier ever sees a Bash call when `Bash` is allowed (the docs say no).

### P2-5: twelve of the eighteen `PreToolUse:Bash` hooks act only on `git` commands but spawn on every Bash call; the `if` field exists for this

`settings.json:108-224` registers eighteen command hooks on `"matcher": "Bash"`. Of these, `fix-commit-requires-test`, `conflict-markers`, `commit-message-guard`, `global-repo-push-guard`, `git-workflow-guard`, `push-eslint-gate`, `push-ruff-gate`, `push-rubocop-gate`, `push-golangci-gate`, `constant-change-guard`, `audit-signal-check`, `llm-rule-judge`, and `build-cheatsheets` each begin by grepping the command for `git commit` or `git push` and exiting otherwise. Each spawn costs a bash plus at least one `jq`. Docs, `hooks.md`: the `if` field takes "Permission rule syntax to filter when this hook runs, such as `"Bash(git *)"`"; "`npm test && git push` ... each subcommand is checked; `git push` matches"; "`$TOOL git push` ... Claude Code can't tell what the command name expands to, so it runs the hook"; "When Claude Code can't determine which commands the Bash input runs, it runs your hook regardless of the pattern." Changelog 2.1.163 fixed the `$()`/`$VAR` over-firing. The hooks run in parallel ("All matching hooks run in parallel"), so wall-clock is the slowest hook, but the spawn count is what `lesson_hook_runtime_budget.md` and `hook-latency.test.sh` are about.

The one real caveat is the same interpreter escape already accepted: `bash -c 'git push'` matches `Bash(bash *)`, not `Bash(git *)`, so an `if`-gated guard skips it where today's text grep would catch the substring. The docs say as much: "Because the `if` filter is best-effort, use the permission system rather than a hook to enforce a hard allow or deny."

Direction: add `"if": "Bash(git *)"` to the advisory and expensive gates first (the four `push-*-gate`s, `llm-rule-judge`, `build-cheatsheets`, `audit-signal-check`, `constant-change-guard`), leave `secret-scan`, `no-em-dash`, `destructive-command-guard`, and `destructive-db-guard` unconditional, and decide the deny-tier git guards (`git-workflow-guard`, `global-repo-push-guard`, `commit-message-guard`, `fix-commit-requires-test`, `conflict-markers`) on whether the interpreter escape is acceptable for them too, since it already is for the permission lists. To confirm: the installed CLI version is at or past 2.1.163 (`claude --version`); `hook-latency.test.sh` measures the chain by invoking scripts directly and would not see the `if` savings, so the fixture needs a settings-driven mode or the expectation stays as is.
