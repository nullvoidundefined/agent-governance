# Security Audit: the Claude harness repository

- **Date:** 2026-07-31
- **Scope:** the entire `~/.claude` harness as an attack surface: 33 hook scripts, `settings.json` permission model, the enforcement bundle under `enforce/`, git history and public-remote exposure, secret-handling controls, and the push-time LLM judge.
- **Role:** Security audit (CISO perspective), `agents/audit-security.md`.
- **Method:** threat model first, then surface enumeration, then evidence-based findings. Every finding pastes the offending code with `file:line`. Private runtime data (`sessions/`, `projects/`, `shell-snapshots/`, `history.jsonl`, cache dirs, client project dirs) was assessed from the outside only; contents were not read.
- **Severity scale:** P0-P3 per R-802. CVSS v3.1 base scores given for the exploitable classes.

---

## Executive Summary

The harness is a security product for a general-purpose agent, and it is well built at the layer it was designed for: pattern-matching secrets in argv, blocking credential-file mutation, gating commit shape, and denying destructive production SQL. Twenty-eight fixture tests back the gates. That layer works.

The layer it was not designed for is the one that matters most now. The harness executes roughly thirty bash scripts automatically on every tool call and session event, with the operator's full privileges, before the permission system is consulted. Several of those scripts hand control to code that comes from the repository the operator happens to be standing in. That inverts the trust model: the safety harness becomes the execution vector.

Three findings dominate the risk posture.

1. **The push gates run untrusted code from the target repository (P0).** `push-rubocop-gate.sh:36` runs `bundle exec rubocop` whenever the repo's `Gemfile.lock` names RuboCop. Bundler evaluates the repo's `Gemfile`, which is arbitrary Ruby, at push time. `push-golangci-gate.sh:58` runs `golangci-lint run ./...`, which compiles and type-checks every package in the tree. Clone a hostile repository, do normal work, run `git push`, and attacker code executes as the operator with no prompt.

2. **The permission allow list grants an unprompted shell, which nullifies the deny and ask lists (P0).** `settings.json:5,40,30,37,34,46,17,14` allow `bash *`, `sh *`, `node *`, `python3 *`, `perl *`, `xargs *`, `env *`, and `curl *` without confirmation. `Bash(bash -lc '...')` matches the allow entry `Bash(bash *)` and does not match any deny or ask pattern, so every catastrophic class the deny list names is reachable in one hop. `PROTOCOL.md:268` records the deliberate replacement of blanket `Bash(*)` with this list; the list does not achieve the stated goal.

3. **The post-execution secret redaction very likely does not redact (P1).** `redact-output.sh:86` sets `suppressOutput: true` and appends a redacted copy via `additionalContext`. In the Claude Code hook contract `suppressOutput` hides the hook's own stdout from transcript mode; it does not remove the tool result from the model's context or the persisted transcript. The hook's own header at lines 7-8 states the opposite belief. `enforce/tests/redact-output.test.sh` asserts only the hook's output shape, so the belief has never been tested end to end. If the reading is right, R-102's entire post-execution half is decorative.

Additionally, R-106 is already breached in published history: the maintainer's real home path and a client-identifying project name were both committed to commits that are on `origin/main`. The push guard cannot catch them because it only inspects the outgoing diff.

**No live credential was found anywhere in git history.** Four pattern matches exist across all 114 commits; all four are synthetic `AAAA...` fixtures inside hook test scripts and hook documentation. Nothing needs rotation on the basis of git history.

## Threat Model

### Assets

| Asset | Where | Why an attacker wants it |
|---|---|---|
| Operator's full user privileges | Every hook process | Hooks are unsandboxed shell running as the operator |
| Live credentials | `~/.claude/.env`, `~/.aws`, `~/.ssh`, gh hosts.yml, keychain | Direct pivot to cloud, git forges, production |
| Session transcripts | `projects/`, `history.jsonl`, `file-history/`, `paste-cache/` | Every secret and every client codebase the operator has touched |
| Client source code | Every repo the operator opens | Confidentiality obligation to third parties |
| The harness itself | `hooks/`, `settings.json`, `enforce/` | Disabling one script silently removes a control for all future sessions |
| The public remote | `github.com/<owner>/claude-global-rules` | Irreversible publication of anything pushed |

### Trust boundaries

1. **Untrusted repository content into hook processes.** The strongest boundary in the system and the least defended. File paths, diff content, constants values, `Gemfile`, `go.mod`, `.enforce.json`, and `docs/audits/*.md` all cross it and are consumed by hooks.
2. **Untrusted text into the agent's context.** Repo files, tool output, web fetches. R-201 governs this by instruction only.
3. **The permission system.** Intended to be the containment boundary. Hooks run *before* it, so hooks are outside it entirely.
4. **The public git remote.** One-way and irreversible. Governed by R-106 and `global-repo-push-guard.sh`.
5. **The network.** `llm-rule-judge.sh` to `api.anthropic.com`, `ntfy-notify.sh` to `ntfy.sh`.

### Attacker personas

- **A1, hostile repository author.** Publishes an attractive repo (a template, a tool, a take-home). Needs only for the operator to clone it and run `git push` or start a session in it. Zero interaction beyond the normal workflow.
- **A2, prompt injector.** Controls text the agent will read: a README, an issue body, a dependency changelog, an MCP response. Aims to get one tool call executed.
- **A3, public-remote observer.** Reads `github.com/<owner>/claude-global-rules` and its full history. Passive, patient, costless.
- **A4, local co-tenant or malware running as the operator.** Wants the transcripts and the credential files, or wants to silently neuter a hook.

### Attack tree 1: repository to remote code execution (most likely, highest impact)

```
Goal: execute code as the operator
+-- Operator clones hostile repo (social engineering, template, take-home)
    +-- Path A: Gemfile RCE                                    [CONFIRMED, P0]
    |   +-- Repo ships Gemfile.lock naming rubocop
    |   +-- Operator commits any .rb file and runs `git push`
    |   +-- push-rubocop-gate.sh:36 selects `bundle exec rubocop`
    |   +-- Bundler evaluates the repo's Gemfile (arbitrary Ruby)
    |   +-- Code runs as the operator, before the permission system
    +-- Path B: Go package analysis                            [CONFIRMED, P0]
    |   +-- Operator commits any .go file and runs `git push`
    |   +-- push-golangci-gate.sh:58 runs `golangci-lint run ./...`
    |   +-- The Go toolchain loads and compiles every package in the tree
    +-- Path C: argument injection into the linter              [CONFIRMED, P2]
        +-- Path in the outgoing diff is crafted as `-r./payload.rb`
        +-- xargs passes it to rubocop as `--require ./payload.rb`
```

**Blast radius:** total. The hook process inherits the operator's environment and filesystem access: `~/.aws`, `~/.ssh`, the login keychain, every client repo on disk, `history.jsonl`, and write access to `~/.claude/hooks/` itself. An attacker who lands here can rewrite the harness to be permanently silent.

### Attack tree 2: prompt injection to unprompted shell

```
Goal: run an arbitrary command with no user confirmation
+-- Inject instructions into text the agent reads (README, issue, MCP output)
+-- Induce a Bash call shaped as `bash -c '<payload>'` or `curl ... | sh`
+-- settings.json allow list matches `Bash(bash *)` / `Bash(sh *)` / `Bash(curl *)`
+-- Deny patterns (rm -rf /, rm -rf ~) and ask patterns (sudo, rm -rf *) do not match
+-- Command executes with no prompt                            [P0]
    +-- secret-scan.sh does not fire: no secret pattern in the command
    +-- destructive-db-guard.sh does not fire: no SQL keyword in argv
```

An adjacent entry point exists at session start: `session-start.sh:61` injects the first 400 lines of a repo-controlled markdown file as `additionalContext` before the operator types anything.

### Attack tree 3: harness self-compromise

```
Goal: permanently disable the secret controls
+-- Any write primitive as the operator (tree 1 or tree 2)
+-- Overwrite ~/.claude/hooks/secret-scan.sh with `exit 0`
    +-- secret-scan.sh's own Write guard does not protect it
    |   (PROT_BASENAME covers .env/.aws/.ssh/.gnupg only, lines 117-118)
    +-- redaction-guard-check.sh still passes: it checks registration
    |   in settings.json and file EXISTENCE, never content (lines 30-40)
    +-- enforcement-guard-check.sh still passes: same, by filename only
+-- Every subsequent session runs unprotected, silently          [P1]
```

## Finding 1 [P0]: push gates execute code supplied by the target repository

- **File:** `hooks/push-rubocop-gate.sh:33-43,58` and `hooks/push-golangci-gate.sh:58`
- **Class:** CWE-829 (inclusion of functionality from an untrusted control sphere) leading to CWE-94 (code injection)
- **CVSS:** 8.6 (AV:N/AC:L/PR:N/UI:R/S:C/C:H/I:H/A:H)
- **Rule context:** the gates exist to enforce R-324/R-327/R-329 analogs. R-107 already treats "hooks sourced from an attacker-controlled location" as a supply-chain signal worth warning about; this is the same class, unguarded.

```bash
# hooks/push-rubocop-gate.sh:33-43
TOP="$(git rev-parse --show-toplevel)"
if [ -n "${CLAUDE_RUBOCOP_CMD:-}" ]; then
  RUBOCOP="$CLAUDE_RUBOCOP_CMD"
elif [ -f "$TOP/Gemfile.lock" ] && grep -q '^    rubocop ' "$TOP/Gemfile.lock" 2>/dev/null; then
  RUBOCOP="bundle exec rubocop"
elif command -v rubocop >/dev/null 2>&1; then
  RUBOCOP="rubocop"
```

```bash
# hooks/push-golangci-gate.sh:58
RESULTS=$(cd "$TOP" && $GOLANGCI run --config "$CONFIG" --out-format json ./... 2>/dev/null || true)
```

**Description.** The RuboCop branch selects its linter based on a file in the target repository and then invokes it through Bundler. `bundle exec` evaluates the repository's `Gemfile`, which is unrestricted Ruby, in order to build the load path. Nothing in that path is a lint operation; it is program execution. The golangci branch is the same class by a different route: `golangci-lint run ./...` drives `go/packages`, which loads, parses, and type-checks the entire module including any `cgo` translation units, so the Go and C toolchains process attacker-authored input with the operator's privileges.

Note the asymmetry with the sibling gate: `push-eslint-gate.sh:36` invokes `node "$HOME/.claude/enforce/lint.mjs"`, whose ESM resolution is anchored to the harness's own `enforce/node_modules`, and passes `overrideConfigFile` so the repo's ESLint config is not loaded. The TypeScript gate got this right. The Ruby and Go gates did not.

**Attack scenario (A1).**
1. Attacker publishes a repository whose `Gemfile` contains a payload alongside legitimate gem declarations, and whose `Gemfile.lock` lists `rubocop`.
2. Operator clones it for any reason: evaluating a tool, reviewing a candidate's take-home, investigating a dependency.
3. Operator does normal work, commits at least one `.rb` file, and runs `git push`. The outgoing diff needs to contain only the operator's own file; the payload does not need to be in the diff at all.
4. `push-rubocop-gate.sh` fires as a `PreToolUse` hook, resolves `RUBOCOP="bundle exec rubocop"`, and executes.
5. The payload runs before the permission system is consulted and before the operator sees a prompt.

**Proof of concept (structure only, not executed).** A `Gemfile` whose first line performs a network callback plus a `Gemfile.lock` containing a line matching `^    rubocop ` is sufficient. The `grep -q '^    rubocop '` check on line 36 inspects only the lockfile text and asserts nothing about the Gemfile.

**Remediation direction.** Two separable decisions. First, for tool selection: prefer a harness-controlled interpreter over one resolved from the target repo's bundle, mirroring the `lint.mjs` pattern that the ESLint gate already uses. Second, for the compiled-language gates: treat "analyzing untrusted source" as inherently privileged and gate it on an explicit per-repo opt-in rather than running by default. An allowlist already exists in this codebase (`enforce/exempt-repos.txt`, read by all four push gates by origin URL); inverting it into an opt-in list for the exec-capable gates reuses machinery that is already there. *To confirm: whether a standalone `rubocop` binary on PATH can lint a bundle-managed repo without the bundle context, since that determines whether dropping the `bundle exec` branch degrades the gate or merely relocates it; and whether `golangci-lint` exposes a type-check-free mode that satisfies the two cops actually mapped in `enforce/golangci-enforce.yml` (mnd, nolintlint).*

## Finding 2 [P0]: the permission allow list grants an unprompted shell, nullifying deny and ask

- **File:** `settings.json:3-68`, especially lines 5, 14, 17, 30, 34, 37, 40, 46
- **Class:** CWE-183 (permissive allowlist) enabling CWE-78-adjacent bypass of the containment boundary
- **CVSS:** 8.8 (AV:L/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H) when chained with prompt injection
- **Precedence:** `PROTOCOL.md:268` documents this list as a deliberate hardening step. The intent is sound; the implementation does not deliver it. Reported as a defect against its own stated goal, not as an undocumented oversight.

```json
"allow": [
  "Bash(bash *)",     // line 5
  "Bash(curl *)",     // line 14
  "Bash(echo *)",     // line 17
  "Bash(node *)",     // line 30
  "Bash(perl *)",     // line 34
  "Bash(python3 *)",  // line 37
  "Bash(sh *)",       // line 40
  "Bash(xargs *)"     // line 46
],
"deny": [
  "Bash(rm -rf /)", "Bash(rm -rf ~)", "Bash(rm -rf ~/)", "Bash(rm -rf $HOME)",
  "Bash(git push --mirror*)", "Bash(gh repo delete*)", "Bash(gh release delete*)"
],
"ask": [
  "Bash(git commit --no-verify*)", "Bash(git push --force*)", "Bash(git reset --hard*)",
  "Bash(git clean -fd*)", "Bash(gh pr merge*)", "Bash(sudo *)", "Bash(rm -rf *)"
]
```

`PROTOCOL.md:268`:

> The blanket `Bash(*)` allow (single-layer posture: hooks were the only gate on shell commands, and the push gates self-describe as evadable) was replaced with a usage-mined allowlist plus ask rules (force-push, `--no-verify`, `gh pr merge` per R-514, `sudo`, `rm -rf`) and deny rules for catastrophic classes.

**Description.** Claude Code matches permission rules against the command prefix. Eight of the forty-four allow entries are general-purpose interpreters or arbitrary-transfer tools. Because the deny and ask patterns are literal command prefixes, wrapping the same action in an allowed interpreter evades them all:

| Blocked form | Equivalent allowed form | Matching allow entry |
|---|---|---|
| `rm -rf ~` (deny) | `bash -c 'rm -rf ~'` | `Bash(bash *)` line 5 |
| `rm -rf <path>` (ask) | `xargs rm -rf <<< "<path>"` | `Bash(xargs *)` line 46 |
| `sudo <cmd>` (ask) | `sh -c 'sudo <cmd>'` | `Bash(sh *)` line 40 |
| `git push --force` (ask) | `bash -c 'git push --force'` | `Bash(bash *)` line 5 |

`Bash(curl *)` on line 14 is separately load-bearing: it authorizes unprompted outbound transfer of arbitrary local files to arbitrary hosts, which is the exfiltration primitive that makes every read-side gap in this report materially worse. `skipDangerousModePermissionPrompt: true` at line 306 removes the remaining friction.

**Attack scenario (A2).** Attacker plants instructions in a README or issue body the agent will read. The agent is induced to emit one Bash call of the form `bash -c '<payload>'`. No hook fires (no secret pattern in the command, no SQL keyword, not a git operation), no permission prompt appears, and the payload runs.

**Remediation direction.** The class of fix is to remove blanket interpreter and transfer entries from the allow list and let them fall through to a prompt, keeping specific narrow forms only if usage data justifies them. The deny and ask lists are not the place to fix this: enumerating wrappers is unwinnable. *To confirm: the exact matching semantics Claude Code applies to `Bash(...)` rules, specifically whether it decomposes compound commands on `&&`, `;`, and `|` before matching and whether any prefix normalization occurs, because that determines whether narrowing the allow list is sufficient or whether the interpreter entries must be removed outright; and the usage-mined frequency data behind the original list, so the removals are made against real friction cost rather than guessed.*

## Finding 3 [P1]: post-execution secret redaction probably does not remove the secret

- **File:** `hooks/redact-output.sh:1-9,85-92`
- **Class:** CWE-1245-adjacent (control that does not implement its stated function); R-102 mechanization gap
- **CVSS:** 6.5 (AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N)

```bash
# hooks/redact-output.sh:4-8 (header, stating the belief)
# PostToolUse hook for Bash. Scans command output for secret patterns and
# replaces them with [REDACTED] before the output reaches the model context.
#
# Uses suppressOutput to hide the raw output and additionalContext to inject
# the redacted version.
```

```bash
# hooks/redact-output.sh:85-92
  jq -n --arg redacted "$REDACTED" '{
    suppressOutput: true,
    hookSpecificOutput: {
      hookEventName: "PostToolUse",
      additionalContext: ("[SECRET REDACTED] The command output contained secret values that were automatically redacted.\n\n" + $redacted)
    }
  }'
```

**Description.** In the Claude Code hook contract, `suppressOutput` is a common hook-output field meaning "hide this hook's stdout from transcript mode." It governs the hook's own output. It is not a mechanism for retracting or rewriting a tool result that has already been produced. If that reading is correct, this hook does not redact anything: it leaves the raw output in place and appends a second, redacted copy alongside it, plus a banner asserting that redaction occurred. The net effect is a false assurance, which is worse than no control, because R-102's design leans on it and `PROTOCOL.md:133` presents the secret layer as covering both directions.

The existing test does not discriminate. `enforce/tests/redact-output.test.sh:9-12` feeds synthetic JSON to the script and asserts on the script's own stdout. It can only ever verify that the hook emits `suppressOutput: true` and a `[REDACTED]` string, which it does. It cannot observe whether the model still sees the original.

**Attack scenario (A4 / accident).** Operator runs any command that prints a credential (`env`, a failing connection string, a vendor CLI echoing config). The secret lands in the model context and is persisted to `projects/*.jsonl` and `history.jsonl`. The banner tells the operator it was handled.

**Remediation direction.** This is a verification task before it is a fix task. The class of fix, if the reading holds, is to move the enforcement to the pre-execution side where a decision can actually be made: `secret-scan.sh` already returns `permissionDecision: "deny"` and already carries the identical pattern list, so extending it to deny commands whose output is predictably secret-bearing reuses an existing control rather than adding one. *To confirm: the authoritative `suppressOutput` semantics for `PostToolUse` in the current Claude Code hook reference, and whether any field exists that can replace or suppress the tool result itself. Run one live command that prints a synthetic `ghp_` fixture and inspect the resulting `projects/*.jsonl` entry for the raw token. That single observation settles the finding.*

## Finding 4 [P1]: the read path is entirely ungated

- **File:** `settings.json:72-165` (PreToolUse matchers), `settings.json:166-176` (PostToolUse matcher)
- **Class:** CWE-200 (exposure of sensitive information); R-102/R-104 mechanization gap
- **CVSS:** 6.5 (AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N)

Confirmed matcher inventory for this settings file:

```
PreToolUse  matchers: "Bash", "Write|Edit"
PostToolUse matchers: "Bash", "Write", "Write|Edit", "TaskUpdate"
```

**Description.** No hook is wired to `Read`, `Grep`, or `Glob`. R-102 reads "keep secret files off-path by default (`.env*`, `~/.aws`, `~/.ssh`, `~/.gnupg`, gh hosts.yml, keychains, browser stores)" and is registered in `enforce/manifest.json` as `regex / hook:secret-scan / error`. But `secret-scan.sh` implements only two things: a pattern scan of outbound content (line 71) and a *mutation* guard (lines 94-129). Its Write/Edit branch at lines 112-129 blocks writing to a protected path; nothing blocks reading one.

The consequence is direct: `Read` on `~/.claude/.env`, `~/.aws/credentials`, or `~/.ssh/id_ed25519` proceeds unmediated, and the content is never passed through any redaction path, because `redact-output.sh` is bound to the `Bash` matcher alone. Grep results over a `.env` file are in the same position.

This audit itself demonstrates the shape of the gap: the role file at `agents/audit-security.md:62` has to state the read boundary in prose, and `rulebook/audits.md:32` (R-805) restates it, because there is no mechanism that could enforce it.

**Remediation direction.** Extend the existing `secret-scan.sh` rather than adding a script: it already owns the protected-path regexes (`PROT_BASENAME` and `PROT_DIR`, lines 117-118) and already emits a well-formed deny. The work is registering it under a `Read|Grep|Glob` matcher and branching on `.tool_input.file_path` and `.tool_input.path`. *To confirm: the exact `tool_input` field names Claude Code supplies for `Read`, `Grep`, and `Glob` (`file_path` versus `path` versus `pattern`), since the existing branch keys on `file_path` and would silently no-op on a mismatch; and whether `PreToolUse` deny is honored for read-family tools in the current runtime.*

## Finding 5 [P1]: private-key redaction strips only the header line

- **File:** `hooks/redact-output.sh:79` (and the mirrored pattern at `secret-scan.sh:68`, `global-repo-push-guard.sh:82`)
- **Class:** CWE-116 (improper encoding or escaping of output)
- **CVSS:** 5.5 (AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N)

```perl
# hooks/redact-output.sh:79
    s/-----BEGIN [A-Z ]*PRIVATE KEY-----/[REDACTED]/g;
```

**Description.** Every other pattern in the list matches a complete token, so substitution removes the whole secret. This one matches a five-word banner. The base64 key body that follows it, which is the actual secret, is untouched and survives into the redacted copy verbatim. A reader of the output sees `[REDACTED]` followed by the entire private key.

The same asymmetry sits in the detection-only consumers: `secret-scan.sh:68` and `global-repo-push-guard.sh:82` use the identical pattern, but there it is harmless because those two only need a boolean, not a substitution. The defect is specific to the substituting consumer.

**Remediation direction.** The fix class is a multiline block substitution spanning BEGIN to END rather than a header match, which also requires the perl invocation to slurp rather than run line-by-line (`-pe` processes one line at a time, so a cross-line pattern will not match as currently invoked). *To confirm: whether switching to `-0777` slurp mode changes behavior for the other twenty-two single-line patterns in the same invocation, and whether the three-file pattern duplication noted at `global-repo-push-guard.sh:15-16` ("keep the two in sync") should be resolved into a shared pattern file first, since a fix applied in one copy and not the others is how this class of drift starts.*

## Finding 6 [P1]: R-106 is already breached in published history

- **File:** git history on `origin/main`; no working-tree file
- **Class:** CWE-200 (information exposure); direct R-106 violation
- **CVSS:** 5.3 (AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N)
- **Value redaction:** per the audit brief, locations only. No path or client name is reproduced in this report.

Two independent leaks, both on commits reachable from `origin/main` (verified with `git branch -a --contains`):

| What leaked | Introduced in | Later sanitized in | Occurrences in patch text |
|---|---|---|---|
| The maintainer's real home path, including the OS username | `ef74f8d` (`docs(audit): engineering audit of restructured rule system`) | `09eedc1` (`docs(audit): sanitize local filesystem paths in the engineering audit report`) | 6 |
| A client-identifying project name | `adfb177` (`docs(rules): add architecture rules R-224, R-225, R-226`) | `a5c0bc8` (`refactor(rules): genericize CLAUDE.md identifiers and stack-tag TypeScript rules`) | 8 |

Neither string appears in the current `HEAD` tree, verified by `git grep`. Both remain fully readable in history to anyone who clones the public repository.

**Why the guard could not catch it.** `hooks/global-repo-push-guard.sh:48` inspects only the outgoing delta:

```bash
ADDED=$(git -C "$ROOT" diff origin/main 2>/dev/null | grep -E '^\+' | grep -vE '^\+\+\+' || true)
```

Once a commit is on `origin/main`, it is by construction absent from `git diff origin/main`. The guard is a leading-edge control with no ability to detect an already-published leak, and the sanitizing commits made the working tree clean while leaving the history untouched. The header at lines 20-23 documents that the check is scoped to the real `$HOME` string and that client-identifying content "stays a context-only rule"; the client-name leak is precisely the case that scoping excludes.

**Attack scenario (A3).** Passive. Clone the public repo, run `git log -p`, correlate the username and client name. Yield: the operator's OS username and local layout (useful for targeted phishing and for guessing paths in a later attack), plus a confirmed client relationship that the repository is explicitly meant not to disclose.

**Remediation direction.** Two separate decisions, and the second is a business call rather than a technical one. Technically, the class of fix is history rewrite plus force-push, which invalidates every existing clone and fork. Whether the exposure justifies that is the operator's call, informed by how long the commits have been public. Independently, the guard should gain a full-history scan so this is detected rather than audit-found; a one-shot `git log -p` scan reusing the pattern block already in the file is the cheap version. *To confirm: how long these commits have been on the public remote and whether the repository has forks or has been cloned by third parties, since a rewrite is only meaningful if the window is narrow; and whether `git log --all -p` over 114 commits stays inside the push hook's latency budget, which `enforce/tests/hook-latency.test.sh` already measures for the per-edit chain.*

## Finding 7 [P1]: no integrity verification of the hook scripts themselves

- **File:** `hooks/redaction-guard-check.sh:30-40`, `hooks/enforcement-guard-check.sh:25-31`, `hooks/secret-scan.sh:112-129`
- **Class:** CWE-353 (missing support for integrity check); CWE-829
- **CVSS:** 7.1 (AV:L/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:N)

```bash
# hooks/redaction-guard-check.sh:30-40
if ! jq -e '[.hooks.PreToolUse[]?.hooks[]?.command // empty] | any(test("secret-scan\\.sh"))' "$SETTINGS" >/dev/null 2>&1; then
  missing+="- secret-scan.sh (PreToolUse) is NOT registered"$'\n'
fi
...
for s in secret-scan.sh redact-output.sh; do
  [ -f "$HOME/.claude/hooks/$s" ] || missing+="- ~/.claude/hooks/$s is MISSING on disk"$'\n'
done
```

```bash
# hooks/secret-scan.sh:117-118 (the paths its own Write guard protects)
      PROT_BASENAME='(^|/)\.env(\.[A-Za-z0-9_-]+)?$'
      PROT_DIR='/\.(aws|ssh|gnupg)(/|$)|/\.config/gh/hosts\.yml$'
```

**Description.** Both session-start guards verify *registration and existence*. Neither verifies *content*. ## Finding 11 [P2]: argument injection into the push linters via repo-controlled paths

- **File:** `hooks/push-rubocop-gate.sh:58`, `hooks/push-ruff-gate.sh:59`, `hooks/single-file-folder-gate.sh:37`
- **Class:** CWE-88 (argument injection)
- **CVSS:** 6.3 (AV:N/AC:H/PR:N/UI:R/S:U/C:H/I:H/A:L)

```bash
# hooks/push-rubocop-gate.sh:58
RESULTS=$(cd "$TOP" && printf '%s\n' "$FILES" | xargs $RUBOCOP --format json --config "$CONFIG" 2>/dev/null || true)
```

```bash
# hooks/push-ruff-gate.sh:59
RESULTS=$(cd "$TOP" && printf '%s\n' "$FILES" | xargs $RUFF check --config "$CONFIG" --output-format json --no-cache 2>/dev/null || true)
```

**Description.** `$FILES` comes from `git diff --name-only` and is entirely repository-controlled. It reaches `xargs` with no `-0`, no `-d '\n'`, and no `--` end-of-options separator before the file list. Two consequences.

First, a path beginning with `-` is parsed by the linter as an option. RuboCop's `-r` / `--require` loads and executes a Ruby file, so a tracked path such as `-r./payload.rb` (a directory literally named `-r.` containing `payload.rb`, which satisfies the `grep -E '\.rb$'` filter on line 30) becomes `rubocop --format json --config <harness> -r ./payload.rb`. That is code execution through the same channel as Finding 1 but without needing a `Gemfile`. The precondition is tighter: the crafted path must be in the *outgoing* diff, so it must be something the operator commits rather than merely clones, which is why this is P2 and Finding 1 is P0.

Second, `xargs` without `-0` applies its own quote and backslash processing, so a path containing a quote character aborts the run with an unterminated-quote error. Both gates treat unparseable linter output as fail-open (`push-rubocop-gate.sh:59-62`, `push-ruff-gate.sh:60-63`), so a single oddly named file silently disables the gate for the whole push. The fail-open itself is a documented and defensible choice; being steerable by repo content is not part of that choice.

`single-file-folder-gate.sh:37` shares the `xargs` pattern (`| xargs -n1 dirname`) but is advisory and stderr-only, so it is noted rather than counted.

**Remediation direction.** The fix class is a `--` separator before the file list plus null-delimited transport (`git diff -z` into `xargs -0`), applied uniformly across the gates. *To confirm: whether RuboCop and ruff both honor `--` as an end-of-options marker in the current pinned versions, since a linter that does not will treat `--` as a filename and fail; and whether `git diff -z --name-only` interacts correctly with the existing `grep -E` extension filters, which are line-oriented today.*

## P3 findings

### P3-1: hooks run `git` inside untrusted repositories with no config hardening

- **File:** every hook that calls `git` without `-C` in the session cwd, e.g. `hooks/audit-signal-check.sh:20`, `hooks/constant-change-guard.sh:22`, `hooks/push-eslint-gate.sh:33`
- **Class:** CWE-829

Git honors repository-local configuration that names external commands: `core.fsmonitor` runs on status and diff operations, `diff.external` and `[diff "x"] textconv` run during diffs, and `core.pager` runs on paged output. A repository obtained as an archive or restored with its `.git` directory intact can carry these. The hooks execute `git rev-parse`, `git diff`, `git log`, and `git grep` in that tree automatically. No `GIT_CONFIG_NOSYSTEM`, no `-c core.fsmonitor=`, no `safe.directory` consideration.

*Remediation direction: pass explicit `-c` overrides disabling the exec-capable config keys on the hook's git invocations. To confirm: which git config keys the installed git version treats as exec-capable in a repository-local scope, since the set has changed across versions and an incomplete list is worse than a documented gap.*

### P3-2: private runtime directory permissions are inconsistent

Observed modes: `sessions/` `700`, `daemon/` `700`, `jobs/` `700`, `ide/` `700`, `history.jsonl` `600`. But `projects/` `755`, `shell-snapshots/` `755`, `file-history/` `755`, `paste-cache/` `755`, `session-env/` `755`, `tasks/` `755`, `backups/` `755`, `telemetry/` `755`, and `.env` `644`.

`projects/` holds full session transcripts and is the single most sensitive directory in the tree; it is world-readable while `sessions/` is locked down. **Mitigating factor, verified:** the home directory itself is mode `750`, so other local users cannot traverse into the harness at all. The exposure is therefore defense-in-depth only, and applies to same-user processes and to any future change in home-directory permissions. Rated P3 on that basis.

*Remediation direction: bring the transcript and snapshot directories to `700` and `.env` to `600` for consistency with the directories that already have it. To confirm: whether Claude Code recreates any of these directories at `755` on startup, which would make a one-time chmod cosmetic.*

### P3-3: no mechanized check that tracked symlinks stay inside the repository

Nine symlinks under `rules/` are tracked (`git ls-files -s` mode `120000`). All currently target `../CLAUDE-*.md` within the tree, verified. A tracked symlink pointing outside the repository would cause the target's content to be read into every session that touches a matching path, and nothing checks the targets. Currently compliant; flagged as an unguarded invariant, not a violation.

### P3-4: documented fail-open gates, as a portfolio

Fail-open is used deliberately and is documented at each site: `llm-rule-judge.sh:6-8` (flaky model must not block work), `push-ruff-gate.sh:7-9` and `push-rubocop-gate.sh:7-8` and `push-golangci-gate.sh:8-9` (missing tool must not block work), `commit-message-guard.sh:5` (unparseable command), `resolveOutgoingBase.sh:43-44` (no base ref). Each individual decision is defensible.

The portfolio-level risk, which no single site can see, is that the number of independent conditions under which a push proceeds with zero enforcement is now large and uncounted: no ruff on PATH, no rubocop, no golangci-lint, no `ANTHROPIC_API_KEY`, no resolvable base ref, unparseable linter output, or a filename that breaks `xargs` (Finding 11). None of these is announced to the operator in a way that accumulates. The stderr notes each hook prints are per-hook and easy to miss.

*Remediation direction: a single session-start or push-time summary of which gates are currently live, so degradation is visible rather than inferred. `enforcement-guard-check.sh` is the existing home for exactly this kind of coverage reporting. To confirm: whether hook stderr reaches the operator's terminal in the current Claude Code UI, because if it already does, the fix is aggregation rather than new plumbing.*

## Section findings by required heading

**Authentication and session management.** Not applicable in the web sense; the harness has no auth surface. The analogous control is the permission system, covered in Finding 2. Session lifecycle hooks (`SessionStart`, `SessionEnd`, `PreCompact`, `Stop`) are covered in Findings 9 and 13.

**Authorization and access control.** The permission allow/deny/ask model is the entire access-control surface and it is bypassable (Finding 2). Hooks execute outside it by design, which is a Claude Code property rather than a harness defect, but it means the hook layer needs to be treated as privileged code, which Findings 1, 7, 11, and 12 all bear on.

**LLM and agent loop security.** Key handling is correct at the one site that uses a key: `llm-rule-judge.sh:47-48` reads `ANTHROPIC_API_KEY` from the environment and passes it in a header, never in argv, which is exactly the pattern `secret-scan.sh`'s header documents as the lesson from the 2026-04-08 incident. The judge has a hard bound (single call, `max_tokens:1024`, `temperature:0`), so there is no tool-call budget or cost-DoS exposure. Prompt-injection surface: the judge feeds attacker-controlled diff content to a model (`llm-rule-judge.sh:45`), but the model's output is constrained to a JSON violations array that can only ever *deny* a push, so injection buys an attacker a denial of service on their own push at most. That is an acceptable exposure and is noted as working-as-designed. The unbounded injection surface is `session-start.sh` (Finding 9), not the judge. Egress and disclosure are Finding 8.

**Input validation and injection.** Every hook reads its input through `jq -r` on a JSON stdin payload, which is the right primitive, and none uses `eval`. The injection exposure is entirely at the boundary where extracted values become *arguments* to other programs: Findings 11 and 12. One `eval`-adjacent construct exists, `llm-rule-judge.sh:28` executing `$CLAUDE_JUDGE_CMD`, discussed in Finding 8.

**CSRF and cross-origin.** Not applicable. No browser surface, no cookies, no origins.

**API security.** One outbound API consumer (`llm-rule-judge.sh`) and one outbound webhook (`ntfy-notify.sh`). Both covered above. No inbound API.

**Secrets management.** Working: no hardcoded credential anywhere in the tree or in 114 commits of history; `.env` and `.env.*` gitignored; the argv pattern list is calibrated with length thresholds so placeholders do not false-positive (`secret-scan.sh:25-27`); the R-103 mutation guard covers both the Bash and the Write/Edit surface and has a fixture test (`enforce/tests/credential-mutation-guard.test.sh`). Not working: Findings 3, 4, 5, and 7. The pattern list is also triplicated across three files with a self-acknowledged sync obligation (`global-repo-push-guard.sh:15-17`), which is how Finding 5's defect could exist in one copy's substitution while the other two remain correct.

**Dependency and supply chain.** Finding 16. Also relevant: Findings 1 and P3-1, which are supply-chain attacks that bypass the dependency layer entirely by executing the target repository directly.

**Infrastructure and deployment.** No containers, no cloud deployment, no HTTPS surface. `SETUP.md` gaps noted under Finding 16.

**File upload and storage.** Not applicable.

**Payment and billing.** Not applicable. No Stripe or billing surface in the harness.

**Data protection.** The harness accumulates a large and long-lived corpus of sensitive data (`projects/`, `history.jsonl`, `file-history/`, `paste-cache/`, `backups/`, `session-env/`) with no stated retention policy and no encryption at rest beyond FileVault. `.gitignore` correctly keeps all of it out of the public remote. Permissions are inconsistent (P3-2). Findings 3 and 4 govern what gets written into that corpus in the first place, which is why they are the higher-leverage fixes.

## Overall Risk Assessment

**Posture: strong at the designed layer, structurally exposed at the layer that now matters.**

The harness was built to defend against the operator's own mistakes: a key pasted into argv, a fix commit without a test, a destructive query against the wrong database, an em dash. Against that threat model it performs well, with mechanical enforcement, fixture tests, and documented tradeoffs at every fail-open site.

It was not built to defend against hostile input, and it now processes a great deal of it. Roughly thirty scripts consume repository-controlled file paths, diff content, lockfiles, and markdown, automatically, with the operator's full privileges, ahead of the permission system. Two of those scripts hand execution directly to code the repository supplies. The permission system that would otherwise contain the damage has an allow list that grants a shell.

The two P0 findings compose badly. Finding 1 gives an attacker code execution; Finding 7 lets that execution permanently silence the controls that would notice; Finding 4 means the credential files are readable without a gate; and `Bash(curl *)` means exfiltration needs no prompt. That is a complete chain from "operator clones a repository" to "operator's cloud credentials are gone and the harness reports healthy."

Nothing suggests this chain has been exercised. No live credential is in history, no unexpected `core.hooksPath` is set, the hook scripts match their documented behavior on inspection, and the working tree is clean. This is a preventive finding, not an incident.

### Prioritized remediation order

1. **Finding 2** (allow list). Highest ratio of risk removed to effort spent. Removing eight interpreter and transfer entries restores the containment boundary the rest of the system assumes, and it is a settings edit.
2. **Finding 1** (push gates executing repo code). Highest absolute severity. The `bundle exec` branch is the urgent half and can be removed independently of the Go decision.
3. **Finding 3** (redaction semantics). Verify before fixing. One live test settles whether R-102's post-execution half exists at all, and the answer changes the priority of Findings 4 and 5.
4. **Finding 7** (hook integrity). Cheap relative to what it protects, and it is what keeps every other fix in this list from being silently reverted.
5. **Finding 4** (read path). Extends an existing hook to three new matchers.
6. **Finding 8** (judge egress) and **Finding 10** (client exclusion). Both are client-confidentiality exposures and both are small edits, one of which is copying an eight-line block that already exists four times.
7. **Findings 11, 12** (argument injection). Mechanical: `--` separators and null-delimited transport.
8. **Finding 6** (published history). Needs a business decision on rewrite before any technical work; the detection improvement can land independently.
9. **Findings 5, 13, 14, 15, 16**, then the P3 set.

### Immediate rotation required

**None.** No live credential was found in git history, in the tracked tree, or in any hook. The four history pattern matches are synthetic test fixtures.

If Finding 3 resolves against the harness (that is, `suppressOutput` does not remove the tool result), then any credential that has ever been printed by a Bash command during a session is sitting in `projects/*.jsonl` and `history.jsonl` in plaintext, and the rotation question becomes a real one scoped by whatever those transcripts contain. That scoping requires reading the transcripts, which is outside what this audit was authorized to do and should be a separate, deliberate exercise.

### Escalation

None of the two escalation conditions in the role definition is met. No finding requires user disclosure (single-operator system) and no finding shows evidence of active exploitation.
