# codex

Most of the Codex configuration is generated from the `claude/` sources in the [agent-governance](https://github.com/nullvoidundefined/agent-governance) monorepo by `translate/codex.mjs`, then copied into `~/.codex` by the repo root's `sync.sh`.

Do not edit `~/.codex` directly, and do not hand-edit a generated file here: change the `claude/` source, run `node translate/codex.mjs --write` from the repo root to regenerate, then `./sync.sh` to install. `node translate/codex.mjs --check` verifies the tree is already current without writing anything; it runs in CI (`.github/workflows/enforce.yml`) and at `git push` (`claude/hooks/pre-push.sample`), so a source edit that never got `--write`ed fails the push rather than shipping stale.

`.claude-port.json` (per-file content hashes) and `PORT-STATUS.md` (the hook-by-hook port table) are themselves generated on every `--write` and carry the current counts. A `GENERATED by translate/codex.mjs` header names the source file each generated file came from; do not edit below that line. A handful of files are hand-authored instead, listed in `translate/codex-port-map.json`'s `hand_authored` array: `hooks/codex-hook-adapter.sh`, its `hooks/approval-state.py` helper, this `README.md`, and the two semantic-render skills (`skills/session-start/SKILL.md`, `skills/session-handoff/SKILL.md`). Edit those source files directly.

The `.gitignore` here is the allowlist of which files under `codex/` git tracks: everything is ignored, then every generated and hand-authored path is named back in. It is generated too, as of 2026-09-17. While it was hand-authored, adding an agent or skill on the `claude/` side needed a matching allowlist line here, and forgetting one left the newly generated file untracked while `--check` still passed, because check compares content and knows nothing about what git tracks. The list is now derived from the planned tree, so a missing entry is a stale file that `--check` fails on.

## Scoped approval for MCP calls

With the default ask policy, the adapter denies an MCP call that requires confirmation and shows an `approve <request-id>` reply. A direct approval of the only pending request also works. The generated `UserPromptSubmit` listener records that reply, and one identical retry can consume it. Arguments, working directory, session, asking hooks, and reasons must still match. Every hook runs again, and a hard denial remains a denial.

Approval expires after ten minutes. One original action can involve several asking hook groups; approval covers their recorded snapshot and reserves all permitted group slots to one retry ID. Unrelated prompts cancel outstanding consent. Replayed prompts, changed inputs, unsafe state files, and unavailable or malformed helper responses cannot authorize a call.

This mechanism requires trusted runtime hooks and a sandbox that prevents ordinary tools from writing the private state directory under the runtime user's home. An isolated Codex CLI 0.158.0 probe verified prompt-before-tool delivery with shared session and turn identities, and verified that a workspace-sandbox tool could not write the runtime-owned probe directory. This establishes that CLI boundary; it does not establish equivalent behavior in every desktop or hosted surface. New hook definitions must pass the runtime's normal hook-trust flow.

Bash and file-edit asks retain their existing behavior. A shell command can refer to mutable external input, such as a PR body file, so matching its command text alone does not establish the same payload. The legacy global allow policy remains compatible but is not enabled by this change. Run the approval fixtures and required security review before installing changes to this mechanism.
