## 0. The central answer (before/after for standard-risk work)

Standard-risk work did move from a lock-enforced RED-first loop to "tests alongside the code". Exact text:

BEFORE (pre-568, claude/rulebook/reference.md R-110 "What the risk decides", and R-412 Scope line 661):
> "A standard-risk slice, even inside a Complex or Saga task, runs Standard mechanics: the session writes the failing test itself under the R-412 lock and implements it, and no per-slice critic runs. ... `tdd.sh` and the lock are the same at every tier and every risk."
> R-412 Scope: "every tier above Trivial (2026-09-06 decision 3)."
> task-start (pre-568, ~line 192 "Standard-risk slice: one session"): "a standard-risk slice runs Standard mechanics under the lock."

AFTER (main):
> reference.md:123 (R-110): "A standard-risk slice, even inside a Complex or Saga task, runs the lean tier (owner decision 2026-10-02, IAN-568, decision 2): no TDD lock, tests written alongside the code that fail when it is wrong (R-401), and one `sonnet` review per PR (R-517); no per-slice critic runs. ... the lock runs only on high-risk slices."
> task-start/SKILL.md:51: "Write the code and its tests together; each test must fail if the code were wrong (R-401); a bug fix starts from a failing test (R-403). No TDD lock, no slice ceremony."
> CLAUDE.md:13 (R-110): "standard-risk runs the lean tier: tests written alongside the code and one sonnet review per PR".

So: the lock (RED observed by tdd.sh, hashes, GREEN proof) is gone for standard-risk. What survives for standard work: R-401 (behavior assertions, mandatory, loaded) and R-403 (bug fixes test-first, mandatory, loaded, but practice only). Nothing observes RED on a feature slice any more. The proposal records the accepted risk (PROP:301): "Tests written alongside the code may be shaped to pass rather than to fail when wrong." Mitigations named: R-401, reviewer checks test strength, `escaped_bugs` on the ticket, `report risk` after ten PRs. No data yet on any of the three (reference.md R-110 Measurement; PROP:125 "introduced 2026-10-01, no data yet").

The owner decision is explicit: PROP:376 decision 2 "high-risk slices only. Standard-risk slices use the lean tier; high-risk slices keep the lock and the triad with I1, I2, I3, I5, and I8 fixed." Note the owner had already moved Voyager standard-risk slices to a lean tier before the proposal (PROP:30).

## 1. Rule-by-rule

### R-110 risk tiers (introduced 2026-10-01, IAN-521, commit 0045ad4 #177)
- Strongest: reference.md pre-568 line 100: classify each slice high/standard; high = auth, sessions, cookies, CORS/CSP, rate limits, trust-boundary validation, SQL construction, secrets, redaction/PII, money, concurrency, or anything the R-109 security-surface detector flags; record `**Risk:**` line at Gate 1, default high when unsure; owner tile per fuzzy control. Enforcement: manual, always. "Deferred" note admits no detector reads the Risk line and nothing checks at merge that a high-risk slice ran the triad.
- Main: loaded in CLAUDE.md:13 (one of 14 mandatory rules); reference.md:114-125. Still manual. Changed only in "What the risk decides" (above) and in the Deferred note (R-907 guard deleted, so "nothing mechanically holds a high-risk slice to a separate test author").
- IAN-568: KEPT, promoted to the switch for everything else (PROP:125 "It is the switch that makes every other cut safe").
- Value: none measured; the idea (spend process where harm is irreversible) is supported indirectly: the only product defects ever caught came from security review, pre-merge review, and behavior tests (PROP:11). 
- Cost: manual, so a misclassification silently picks the wrong process; default-to-high-when-unsure biases toward the expensive path. Heuristic list is long and includes "retries" and "queues", which pull a lot of ordinary code into high-risk.

Reasoning, PRACTICE: The proposal removed the observable-RED discipline from standard work to cut a ~20-30 min/PR tax, and accepted that tests may be "shaped to pass". The recorded catches say behavior tests and independent review find defects; they do not say a lock does, and the lock's visible costs are large. Still, "write the test, see it fail for the right reason" is the cheapest independent signal that a test can fail at all, and the lean tier now relies on a reviewer noticing a vacuous test. A reasonable recovery position is: reinstate a practice-only "see RED once" step for standard-risk features (run the new test against the pre-change code, or stash the fix, once, and say so in the PR body), at zero hook cost, because R-403 already makes this mandatory for bug fixes and the same reasoning applies to new behavior. That costs 1 to 3 min per slice, not 20 to 30, because it drops tdd.sh, hashes, role agents, the dirty-lock states, and the DISPUTE loop. Do not reinstate the lock for standard-risk.
Reasoning, MECHANISM: The lock is correct for the one place the owner has accepted exceeding budget (security/money/concurrency) and has now had its three biggest stall causes patched (I1, I2, I3, I5, I8). Keep it narrow. Biggest open weakness: I1 turns collateral edits into per-file owner asks and the whole lock still depends on classification being right (manual). The triad's marginal value over "same-session test + fresh-context reviewer" is unmeasured; the per-slice critic has no recorded catch. The watchdog is a necessary add-on to any retained subagent dispatch (IAN-605). R-509 and fix-commit warning are cheap and should stay.

Questions the data cannot answer (for the proposal): (a) whether escaped_bugs on standard-risk tickets will rise (needs the 10-PR rollup); (b) whether the I1 ask recreates owner latency; (c) whether tests-after-code would have missed the voyager parser/PII defects (those catches were by R-401 tests and reviewer, which survive).
