# Skills Audit: 2026-09-17

Scope: the 15 user-authored skills under `claude/skills/`, which are the canonical sources, plus their generated copies under `codex/skills/` and hand-ported copies under `cursor/skills/`. Two questions were asked of every skill. First, can the skill be improved as written: is it accurate against the rules, hooks, agents, and scripts it cites, and does it tell the model what to do without asking it to remember something a script could check. Second, does the skill contain a requirement that a deterministic script could satisfy or verify, so that compliance stops depending on recall (R-516, `global-memory/feedback_mechanize_structure_rules.md:8`).

Read in full: every `claude/skills/*/SKILL.md`, `claude/CLAUDE.md`, `claude/rulebook/{reference,agents,audits,cost}.md`, `claude/enforce/README.md`, `claude/enforce/manifest.json`, `claude/enforce/tdd.sh` (header and dispatch), `claude/hooks/{spec-glossary-check,session-start,session-end,verification-gate,hook-integrity-check,enforcement-guard-check,git-workflow-guard,commit-message-guard,content-gate}.sh` (the parts each skill relies on), all 13 agent front matters, `claude/prompts/*.md`, `translate/*.mjs`, both port maps, `claude/ISSUES.md`, the 2026-09-16 engineering audit (P2-10) and the 2026-09-06 TDD harness assessment, the current handoff, and the Claude Code skills reference (`code.claude.com/docs/en/skills.md`, fetched 2026-09-17) for the frontmatter fields the recommendations below cite.

Run, not just read: em-dash scan over the skills (zero hits); closure of every `~/.claude/...` path a skill cites against the tree (all resolve; `KNOWN-ISSUES.md` is gitignored by design and the skill says so); closure of every `R-NNN` a skill cites against the four rulebook files (all resolve); frontmatter field inventory (every skill carries `name` and `description` and nothing else); `description:` line lengths including the key (119 to 500 bytes, 3,957 in total, which is what the skill listing costs every session before truncation); a per-skill diff of `claude/skills` against `cursor/skills` with the generated header excluded.

Not verified: the Superpowers plugin skills that `task-start`, `feature-create`, `task-cleanup`, and `tdd-gated-dispatch` delegate to (`brainstorming`, `writing-plans`, `executing-plans`, `subagent-driven-development`, `test-driven-development`, `finishing-a-development-branch`) are not in this checkout, so their names are taken from `claude/README.md:29`. `/skill-doctor` needs a live session and was not run; its numbers would settle the two context-cost findings below.

The Cursor copies have no generator (`cursor/README.md`: "ported by hand from that source") and no check. Diffing each pair with the generated header excluded:

The `task-start` drift is substantive, not cosmetic. `cursor/skills/task-start/SKILL.md` Standard tier reads:


where the source (`claude/skills/task-start/SKILL.md:60`) reads:

```
TDD:            Yes, as slices under the lock: tdd.sh open, failing test, tdd.sh red, implement, tdd.sh green, close (R-412).
```

The Cursor `tdd-gated-dispatch` is the pre-2026-09-06 version of the skill (the one the TDD harness assessment rewrote, `docs/audits/2026-09-06-tdd-harness.md:177`). A Cursor session that follows it has the primary agent write the tests and dispatch an implementer told "do not modify the pre-written test files", with no lock, no `tdd.sh`, and no role policy. Either way, a fixture (part of X-2 below) that diffs each `cursor/skills/*/SKILL.md` body against its source, header excluded, turns the next drift into a red check. `to confirm:` whether any Cursor session has actually invoked `tdd-gated-dispatch` since 2026-09-06; if Cursor is not used for TDD work, the fix is the re-clone plus the fixture, not a renderer.

### X-2: nothing lints the skills, so every property this audit checked by hand can regress silently

**Severity: P1.** Governing rules: R-516 (a mechanizable check with no fixture depends on recall); the closure precedent in `claude/enforce/tests/claude-md-lint.test.sh:30`, which is the only test that reads `skills/*/SKILL.md`, and reads them only for `R-NNN` norm lines.

The properties checked for this audit, all decidable from the files alone, and none currently tested:

1. Frontmatter parses and `name` equals the directory name (the translator throws on a missing name, `translate/parse-sources.mjs`, but only when the translator runs, and nothing checks the name matches the directory).
2. Every `~/.claude/<path>` a skill cites exists in `claude/` (or is on the gitignore list with the skill saying so, as `known-issues` does).
3. Every `R-NNN` a skill cites has a Spec block in one of the four rulebook files. The 2026-07-31 P3 "no ID-closure guard for R-7xx/8xx/9xx references" in `claude/ISSUES.md` is this gap; the skills cite R-701 through R-707, R-804, R-901, R-903, and R-907, and the existing lint checks none of them.
4. No U+2014 (R-207). `no-em-dash.sh` catches a Write at runtime; nothing catches a merge, a hand edit, or a port.
5. Every `superpowers:<name>` a skill names is one of the twelve `claude/README.md:29` lists.
6. Every `docs/<path>` output location a skill writes to is spelled the same way in every skill that names it (`docs/audits/`, `docs/superpowers/specs/`, `docs/superpowers/plans/`, `docs/superpowers/backlog.md`, `docs/slices/`, `docs/feature-list/features.md`, `docs/user-stories/`, `docs/query-params.md`, `docs/session-handoff/session-handoff.md`).
7. The rule-id list in the `structure-conventions` description matches the rule ids its body carries (17 today; both were checked by hand and agree).
8. The Cursor body diff from X-1.

**Fix direction.** One fixture, `claude/enforce/tests/skills-lint.test.sh`, following the `claude-md-lint.test.sh` shape (env-overridable paths, one FAIL line per property, a PASS line with counts). Checks 1 through 5 and 7 are a few `grep`/`comm` lines each; check 6 is a table of expected paths; check 8 is the diff from X-1. This is the highest-leverage script in this report because it protects every other finding's fix. `to confirm:` whether the test should also fail on a description over 1,536 characters (the documented truncation point for `description` plus `when_to_use` in the skill listing); none is close today, so it is a guard against future growth rather than a current defect.

### X-3: every skill is model-invocable, including four that delete files, write a database, create worktrees, or commit

**Severity: P2.** Governing rules: R-105 (explicit confirmation before destructive actions), R-101 (managed-DB writes), R-514 (merge authorization); the documented `disable-model-invocation` field.

Every skill's frontmatter is exactly `name` and `description`. The skills reference documents that a skill with the default frontmatter can be loaded by Claude on its own judgement whenever the description matches, and that `disable-model-invocation: true` restricts it to a user `/name` invocation and removes its description from the always-loaded listing. Four skills perform actions that should not start on a description match:

| Skill | Action the skill takes on its own | Where |
|---|---|---|
| `cleanup-specs-plans` | `git rm` of spec and plan files, then a commit | `SKILL.md:86-87` |
| `resolve-user-feedback` | `UPDATE app_feedback SET status = 'closed'` against staging or production | `SKILL.md:94` |
| `feature-create` | `git worktree add`, `pnpm install`, a commit | `SKILL.md:47-53`, Step 6 |
| `all-hands` | Nine agent dispatches and a committed report | Steps 1 to 3 |

The hooks catch parts of this (`destructive-db-guard` for DELETE and DROP but not UPDATE, `commit-message-guard` for the subject, `mcp-action-guard` for MCP verbs), but the cheapest gate is not loading the skill unless the user asked for it. The same four are the ones whose descriptions consume listing context on every session for a workflow that runs at most weekly.

**Fix direction.** Add `disable-model-invocation: true` to those four. Consider `argument-hint` on `feature-create` (`<slug> [plan-path]`, the skill's own Invocation section), `gof` (`[file|feature|area]`), and `bug-hunt` (`[path|range]`), so the `/name` form documents its arguments where the user types them. `to confirm:` the installed Claude Code version honours `disable-model-invocation` for user-level skills (the doc states it; `/skill-doctor` on v2.1.252 or later reports which skills were never invoked, which is the number that decides whether `all-hands` belongs in the always-loaded listing at all).

### X-4: "Announce at start" is on five skills and absent from ten, with no rule deciding which

**Severity: P3.** Governing rule: R-209 (delete action announcements) versus R-503 (announce share and timestamp for any skill execution).

`build-by-slice-require-review:10`, `feature-create:12`, `spec-grounding:12`, `task-cleanup:10`, and `task-start:10` open with an "Announce at start" line. The other ten do not. R-209 says to delete action announcements; R-503 says any skill execution announces its share of work and captures a start timestamp. The five announcements satisfy neither: they name the skill but carry no share and no timestamp. The Superpowers skills the harness composes with use the same announce line, which is probably where the convention came from.

**Fix direction.** Decide once in `PROTOCOL.md` Layer 2 (`claude/PROTOCOL.md:60` is where skill invocation is described): either every skill announces in the R-503 form, or none does and R-503's ledger is written by `task-start` alone (see T-2 below, which gives R-503 a file to write to). `to confirm:` whether R-209's "action announcements" was meant to cover skill invocation; the rule predates R-503.

## Per-skill findings

### `all-hands`

**A-1 (P2): "Use Sonnet for all roles" silently overrides four role files that set Opus, and the skill does not say how.** `SKILL.md:32` and `:95` say Sonnet for all roles. `agents/audit-engineering.md:5`, `audit-security.md:5`, `audit-criticism.md:5`, and `audit-customer.md:5` set `model: opus`. When the Agent tool is called with `subagent_type` naming a role file, the role file's model applies unless the call passes a `model` override, so a session following the skill either dispatches on Opus (ignoring the skill) or passes an override the skill never mentions. Fix direction: state the mechanism ("pass `model: sonnet` on every dispatch; the role file's `model` is the default for a full audit, not for this scan"). `to confirm:` that an Agent-tool `model` argument overrides the agent-file value on the installed version; if it does not, the skill needs nine `-scan` variants or has to accept the role-file models.

**A-2 (P2): the lightweight prompt drops the R-804 restatement that every audit dispatch must carry.** `rulebook/audits.md` R-804 Scope: "audit dispatch prompts restate (a) through (c)"; R-701 Spec says the same. The prompt at `SKILL.md:28` asks for one-sentence bullets and nothing about pasted evidence, precedence, or fix-as-direction. For a pulse check that is a deliberate trade, but it is undeclared, and R-802 P2/P3 routing to `ISSUES.md` is also unmentioned. Fix direction: one sentence in the prompt that the R-804(a) evidence requirement is waived for this format and that every bullet still names the file or surface it is about, plus a line in the skill that P0 items go to the current effort and the rest wait for the role's full audit.

**A-3 (P3): the output writer is scriptable but low value.** Dedup of "same issue flagged by two roles" is semantic. The mechanical part (sort by priority, render the top table and the nine per-role sections at the R-802 path, refuse a bullet without a `[P0/P1/P2]` tag) is small. Candidate rating: low; do it only if the fixture in X-2 grows a generic "audit report shape" check.

### `bug-hunt`

**B-1 (P2): the default scope `git diff HEAD~5` fails on a repo with fewer than five commits and misreads merges.** `SKILL.md:24,29`. On a branch of three commits `HEAD~5` is an error; across a merge commit `HEAD~5` walks the first parent and the diff includes the merged branch's whole history. Fix direction: resolve the range as `git merge-base origin/main HEAD` when on a branch, else the last N commits capped at `git rev-list --count HEAD`; the skill already has `hooks/../enforce/resolve-outgoing-base.sh` doing the branch half of this for the push gates. `to confirm:` that `resolve-outgoing-base.sh`'s fallback order (`origin/main`, `main`, `origin/master`, `master`) is the one wanted here.

**B-2 (P2): two of the ten checks are mechanical, and a third is already the linter's.** Step 4 "Check if deleted files are still imported elsewhere" is `git diff --diff-filter=DR --name-only <range>` followed by a grep for each old basename in import specifiers; a model reading files misses this more often than a grep does. "Type safety gaps (`any` usage)" (`SKILL.md:41`) is R-329, enforced by `eslint:no-explicit-any` and `eslint:ban-ts-comment`, and the skill's own "What NOT to Flag" excludes lint findings, so the model is asked to re-derive what `lint.mjs` reports. Fix direction: Step 3 opens by running `node ~/.claude/enforce/lint.mjs` over the changed files and a dangling-reference script (candidate S-6 below); the model's pass then covers only what neither decides. Candidate rating: medium.

**B-3 (P3): the report goes to chat, not to `docs/audits/`.** Consistent with the skill being a diff-level tool rather than an R-802 role, but `all-hands` and the role agents write files and `bug-hunt` does not, and the skill does not say which it is. One line either way.

### `documentation-create`

**E-1 (P3): the red-flag list is partly regex-able as an advisory.** `SKILL.md:72-80` lists seven patterns; four are detectable with acceptable false positives: a superlative with no "because" in the same sentence (`the most|the best|the worst|the sharpest`), a comparative with one side (`-er than` at sentence end), an absolute (`never|cannot|always`) about behaviour, and a number followed by a plural noun with no colon or list within the next three lines. As a PostToolUse reminder on `docs/**/*.md` writes it would fire on every draft, which is the point of an advisory; as a script the author runs once it is cheaper. **E-2 (P3): "Failure modes observed in testing" is rationale.** `SKILL.md:51-60`, ten lines describing an experiment, in a model-facing file (R-206). The four faults table and the verification contract carry the instruction; the experiment is the "why". Keep it if the examples change behaviour; otherwise move it to a `reference.md` beside the skill, which the doc's bundling convention supports and which does not load until read.

**E-3 (P3): R-210 is the rule this skill implements and it is not cited.** R-210 ("complete sentences with full context, leaning toward verbose") landed 2026-09-16, after this skill; the skill's opening paragraph is R-210 restated. ### `feature-create`

**F-1 (P2): Steps 1 through 4 and 6 are shell, and the skill asks the model to run them one at a time and "stop and report if any step fails".** `SKILL.md:28`. Parsing the slug, checking `git branch --list`, checking the worktree directory, `git worktree add`, `pnpm install`, `pnpm test`, appending the feature-list row, writing the user-story skeleton, and the scaffold commit are one script with exit codes. The model's contribution is Step 5b's acceptance criteria (read from the plan) and Step 7's execution recommendation. This is the strongest single-skill candidate in the set; see S-1. `to confirm:` the stack assumption the skill already states (pnpm, `docs/feature-list/`, `docs/user-stories/`); the script takes the install and test commands as arguments or reads them from `package.json` scripts, and skips a scaffold whose directory the project lacks, which is what the skill's own note says to do.

**F-2 (P2): two latent failures in the shell as written.** `SKILL.md:53` `test -d ../<project>-worktrees/<slug>` and the `git worktree add ... -b feat/<slug> main` in Step 3 both assume the session's cwd is the project root and that the default branch is `main`, with no fetch first, so the worktree branches from a possibly stale local `main`. A project whose default branch is `master`, or a session started in a subdirectory, fails at Step 3 with a message the skill does not anticipate. Fix direction: resolve the root with `git rev-parse --show-toplevel`, the default branch with `git symbolic-ref refs/remotes/origin/HEAD`, and fetch it before branching; all three are one line each in S-1.

**F-3 (P3): Step 5d asks the user a y/n question in the middle of an otherwise unattended flow.** "Does this feature introduce new query parameters?" is answerable from the plan (grep for `searchParams`, `query`, `?`-bearing routes) with a default of no; ask only when the plan mentions one. **F-4 (P3): the worktree location differs from Claude Code's.** `feature-create` puts worktrees at `../<project>-worktrees/<slug>/`, and `hooks/parallel-session-check.sh:72` tells a session to `git worktree add ../<name>`, so the harness consistently uses a sibling directory; Claude Code's built-in worktree tool uses `.claude/worktrees/` inside the repo.
