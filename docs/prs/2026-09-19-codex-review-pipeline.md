# Codex authors every test and reviews every spec and PR

Refs: IAN-101

## Summary

The owner made three decisions on 2026-09-19 that move Codex (OpenAI's coding agent, run through its CLI as a separate process) from an occasional Standard-tier test author to a fixed second model at three points of every task. First, Codex writes the failing test for every slice in the Standard, Complex, and Saga tiers, and Claude's `test-author` subagent writes it only when Codex is unavailable or rate-limited, with that fallback recorded on the slice. Second, Codex reviews every PR's diff against the spec and the acceptance criteria before merge, as a blocking step beside the Copilot review, and the PR body carries a `## Codex review` section with each finding and its disposition. Third, task-start runs an adversarial Codex review of every Complex and Saga spec, including a two-sided stack and build-versus-buy audit, after the spec is written and before the owner approves it and before writing-plans. The second decision is enforced mechanically as the new rule R-517; the other two are process text in the skills and rulebooks.

## What changed

## Architectural decisions

- **Chosen: extend `git-workflow-guard.sh` rather than add a new hook.** It already parses `gh pr merge`, forwards the PR selector and `--repo`, and runs `gh pr view` under a deadline for R-512's bundle check, so R-517 reuses that one gh call (R-308). **Alternative:** a separate `codex-review-merge-gate.sh`. **Why not:** it would duplicate the parser and the deadline runner, and two hooks would each call gh on every merge.
- **Chosen: every merge now consults gh, squash included.** Before this change a squash merge was decided from the command alone. **Alternative:** check only when a ticket or tier says the PR is non-trivial. **Why not:** the owner's decision says every PR, and a gate that can be skipped by tier would need the tier ledger, which a merge from another session does not have.
- **Chosen: the hook checks presence and non-emptiness only.** Whether each finding was really fixed or answered is a judgment, so it stays manual. **Alternative:** parse a findings table and require a disposition column. **Why not:** the fallback reviewer and a "No findings" review both produce legitimate sections with no table, and a format check would push toward filling a table rather than doing the review.
- **Chosen: the spec review and test authoring are process text, not hooks.** A spec review happens before any command the harness can observe as its trigger, and a Codex-written test is invisible to Claude's hooks by construction; `tdd.sh validate test-author` is the mechanical check for the latter and is named in the skill. **Alternative:** a push gate requiring a `## Spec review` section in any new spec. **Why not:** judged not worth it now, because the existing spec-glossary reminder fires on the spec Write and a spec reaches the owner's approval in the same session that writes it; this can become a reminder later if specs skip the step.
- **Chosen: the review fallback is a separate Claude agent on an equal or stronger model, never the main session** (owner decision relayed during this task, which corrected an earlier instruction that named the main session).

## Codex review

This PR dogfooded R-517. Codex was invoked with the new PR review prompt and returned "You've hit your usage limit" (reset at 6:00 PM), so the fallback ran: a separate Claude agent on `fable` in a fresh context with the same prompt, over `origin/main...b8d3cef`. It reported six findings. Four were fixed in 6ddaf58 (two merges in one command, `--repo` before `merge`, a heading inside a fenced block, and rule text naming the wrong gh fields), one fixture weakness was fixed in the same commit (the `--merge` assertion could not detect a gh call), and one was answered: the fallback-model wording says "at least as strong, ideally stronger", which matches the owner's "ideally on a stronger model".

Copilot's first round then found five more, all valid and all fixed test-first in the follow-up commit: line continuations and `env`/`command`/path forms of `gh` still slipped past the merge matcher; a command mixing a parseable merge with an unparseable one was judged by the first PR only; a fence could be closed by the other fence character; a four-space indented code block counted as a heading; and `tdd.sh validate test-author` cannot see a Codex commit or a lock edit, so the skill and R-907 now record HEAD and the lock hash before the Codex run and require both unchanged after it.

Because that round changed behavior, R-517 required a re-review of `fcfb268...c5a6274`; Codex was still over its limit, so the same fallback (a Claude subagent on `fable`) ran it and found four more, all fixed test-first in the next commit. The HIGH one was a regression of my own: adding `(` to the broad merge matcher made a commit message containing "(gh pr merge" read as an unparseable merge and be denied, so `(` is out again and a subshell merge is recorded as a known limit, as it always was for R-512 and R-514. The wrapper list grew (`timeout`, `nice`, `xargs`, `eval`, `bash -c`, an escaped or quoted `gh`, wrapper options with values), an escaped backslash no longer joins lines, HTML comments no longer count as the section, and a fence no longer closes on a line with trailing text. The rule text now says plainly that the wrapper list is a denylist and cannot be complete.

Copilot's second round and a third fallback review then showed the pattern: each regex fix either left a sibling shape open (brace groups, subshells, `if ... then`, quoted `pr` or `merge`, `cd` inside braces) or denied an ordinary command (a commit message starting with a wrapper word, an HTML comment on a real section line). So the merge detection stopped being a regex. The quote-aware shell tokenizer that `pr-ticket-ref-gate.sh` already used moved into `claude/hooks/shell-command-tokens.sh`, and `git-workflow-guard.sh` now classifies each simple command the shell would actually run, recursing into `eval` and `sh -c` strings. Any merge that is not a bare `gh pr merge` on its own simple command is denied as unparseable, any `cd`/`pushd`/`popd` anywhere denies, and quoted arguments and heredocs are never read as merges. The section detector now strips inline HTML comments and code spans instead of discarding the whole line. Copilot also found that the Codex test-author lock check could never pass if Codex ran `tdd.sh red`, which rewrites the lock, so the prompt now tells Codex not to run `tdd.sh` and the orchestrator runs `red` after the hash check.

A fourth fallback review of the rewrite found the remaining ways around it, all fixed test-first: a merge fed to a shell through a heredoc or a pipe, a backtick substitution, words built by expansion (`$'merge'`, `mer${x}ge`, `$g pr merge`), flags read from a quoted mention instead of the real merge (the parser now reads the scanned words of the one canonical merge), and an over-broad deny when the tokenizer helper is missing. The first CI run of the rewrite also failed where macOS passed. bash 5.2 on the Ubuntu runner enables `patsub_replacement`, which processes backslashes in a `${var//pattern/replacement}` replacement and turned the escaped-backslash marker back into a line continuation. Quoting the replacement is not portable, because bash 3.2 then inserts the quotes literally, so the hook switches the option off. The fixture now prints the failing line through an ERR trap, which is how CI named the case.

## Reflection

Committed at 13:28 and 13:41 on 2026-09-19; this document was written a few minutes after the second commit. The main thing I understand now is that the pre-merge gate was only as strong as the merge parser under it: the parser predates this change and read only the first `gh pr merge`, which was harmless while squash merges never consulted gh and became a real bypass the moment every merge had to prove something. The review caught that, and it also caught that my first fixture line for the `--merge` path could not fail for the reason its comment claimed. I also first wrote the heading match with regex intervals, then removed them because older mawk on the Ubuntu CI runners does not support them, the same lesson an earlier PR in this repository recorded.
