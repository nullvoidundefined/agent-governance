# tdd.sh runs pytest slices

Refs: IAN-124

## Summary

`enforce/tdd.sh` is the tool that proves a slice's RED and GREEN and writes the `.claude/tdd-lock.json` that `hooks/protected-path-guard.sh` enforces (R-410, R-412). Until now it chose between two runners, the bash fixture runner for `*.test.sh` paths and Vitest or Jest for everything else, and it deferred pytest, go test, and RSpec until the first project on each stack arrived (2026-09-06 decision 1). The first Python project has arrived: the FastAPI template is about to build `apps/server` as a uv project tested with pytest, and its first slice cannot run under the lock until `tdd.sh` understands pytest. This change adds a pytest runner whose results are converted into the same JSON report shape the other two produce, so `red`, `green`, `open --refactor`, and `validate` work unchanged and keep exactly the semantics they already have.

## What changed

- `select_runner` now sorts the named test paths into three kinds: `*.test.sh`, `*.py`, and everything else. More than one kind in a slice is refused with the count of each, which keeps the existing rule that a slice never mixes runners.
- `resolve_pytest` walks up from each named file to the nearest directory holding `pyproject.toml`, never above the repository root, and refuses named files that belong to two different projects. It runs pytest there under `uv run python`, the project environment `uv run pytest` uses, when `uv` is on PATH; otherwise under the project's `.venv/bin/python`, then `python3`, then `python`, and prints a warning. In both cases pytest starts through `PYTEST_BOOTSTRAP`, a few lines passed with `-c` that set `sys.pycache_prefix` to a fresh directory, disable bytecode writes, drop the current directory `-c` puts on `sys.path`, and call `pytest.console_main()`. `CLAUDE_TDD_UV` overrides the uv binary name, which the fixture uses to exercise the fallback.
- `run_pytest_suite` runs the whole suite once with `--rootdir` pinned to the project, `-o junit_family=xunit1 --junitxml=<tmp>`, `--continue-on-collection-errors`, and `-p no:cacheprovider`, with the bootstrap's bytecode directory deleted after the run. `pytest_report` converts the XML with a short inline Python script using only the standard library, run by `project_python` (the project's `.venv/bin/python`, then `python3`, then `python`) or, when none of those exists, by `uv run --no-project python`. When no report can be built, pytest's last fifteen output lines go to stderr beside the existing "produced no JSON report" refusal.
- The pytest failure classes are `ModuleNotFoundError|ImportError` for the missing-module RED, `AssertionError|DID NOT RAISE` for the assertion RED, and `SyntaxError|IndentationError|TabError` for a test that does not parse. A pytest file with no tests is refused with a hint that pytest may not have collected it, because pytest reports nothing at all for such a file, which is indistinguishable from a file outside `testpaths`.
- The header comment of `tdd.sh` describes the pytest runner and now defers only go test and RSpec. `claude/enforce/README.md` and `claude/ISSUES.md` say the same.
- New fixture `claude/enforce/tests/tdd-pytest.test.sh`, and a pinned `pipx install pytest==9.1.1` step in `.github/workflows/enforce.yml` beside the ruff install, so CI runs the fixture against the real pytest instead of skipping it.
- `claude/enforce/hook-hashes.txt` is regenerated. No manifest entry changes: R-412's enforcer is `hook:protected-path-guard`, which other fixtures cover, and `tdd-red-green.test.sh` carries no `Covers:` line either. The Cursor and Codex ports regenerate with no changes.

## Architectural decisions

- **Chosen: parse pytest's built-in `--junitxml` output.** JUnit XML ships with pytest, so the runner adds no dependency to the projects it governs, and Python's standard library parses it. **Alternative:** `pytest-json-report`, which emits JSON directly. **Why not:** every governed project would have to add a plugin to its dev dependencies before its first slice could run, and a slice tool that fails on a missing plugin is a setup trap; the plugin also has a smaller maintenance base than pytest itself.
- **Chosen: the xunit1 JUnit family.** pytest's default family, xunit2, drops the `file` attribute, which leaves only the dotted `classname` to map a test back to its file, and that mapping is ambiguous for packages and nested classes. xunit1 carries `file` relative to the rootdir, so each record is named by the file's absolute physical path exactly as the Vitest report names it, and `--rootdir` is pinned so that relative path is always relative to the project directory.
- **Chosen: `--continue-on-collection-errors`.** Without it, one test module that fails to import stops pytest before any other file runs, which reports an outside baseline of zero for exactly the missing-module RED this runner has to accept. The fixture proves this: without the flag it fails with "the pytest baseline must count the passing test outside the RED file, got 0".
- **Chosen: collection errors become file records with no tests and the error as the message.** That is the shape Vitest produces for a file that fails to load, so the existing `classify_red` branches (parse failure refused, missing module accepted, unclassified refused) and the `green` "failed to run" refusal apply without a pytest-specific code path.
- **Chosen: bytecode confined to a fresh per-run cache, set from inside the interpreter.** Python trusts a cached `.pyc` whose recorded source mtime (whole seconds) and size match the source, so bytecode left in the tree by an earlier run, whether the developer's own `pytest` or a RED run, can survive a same-size implementation edit made within the same second, and the GREEN run then executes the old implementation. That is a false GREEN, the one failure this tool exists to prevent. The bootstrap sets `sys.pycache_prefix` to a directory created for the run and deleted after it, and sets `sys.dont_write_bytecode`, so a `.pyc` in the tree is never consulted and none is left for `tdd.sh validate` to attribute to a role. **Alternative:** `PYTHONDONTWRITEBYTECODE=1` alone, which the first commit on this branch used. **Why not:** it stops writes but not reads, so bytecode the developer's own run left in the tree was still trusted; the fixture's stale-bytecode case (the passing implementation compiled in place, then replaced by a failing one with the same size and mtime) reported GREEN under it. **Alternative:** `PYTHONPYCACHEPREFIX` and `PYTHONDONTWRITEBYTECODE` in the environment of `uv run pytest`, which a later commit on this branch used. **Why not:** CI's pytest is a pipx console script whose shebang is `python -E`, and `-E` makes Python ignore every `PYTHON*` variable, so the stale case still went GREEN there; any console script built the same way would do the same. **Alternative:** `python -B -X pycache_prefix=<dir> -m pytest`. **Why not:** `-m` puts the current directory at the front of `sys.path`, which the pytest console script does not, so a test could import a module under `tdd.sh` that it cannot import under `uv run pytest`; the bootstrap removes that entry before pytest starts. **Alternative:** delete `__pycache__` directories before each run. **Why not:** it writes to the developer's tree, and it cannot cover bytecode written during the run.
- **Chosen: the converter runs inline under the project's interpreter first.** A separate script file would add a Python file to the harness for the push-time ruff gate and the integrity hashes to track for about thirty lines. The interpreter order (`.venv/bin/python`, `python3`, `python`, then `uv run --no-project python`) means a project that relies on its own virtual environment without a global Python still gets a report; the first commit required `python3` on PATH, which Copilot's review caught. **Alternative:** convert in `jq` or node. **Why not:** neither parses XML without a dependency.
- **Chosen: a stub `uv` and a stub `.venv` interpreter in the fixture, each forwarding to the real pytest.** The stubs record the working directory and arguments, so the fixture observes the invocation choice (`uv run pytest` from `apps/server`, and the `-m pytest` fallback) rather than assuming it, while pytest's real JUnit output is what gets parsed. Running the real `uv run pytest` in the fixture would need network access to build a project environment.

## Testing

- The fixture builds a repository whose Python project sits at `apps/server`, below a git root with no `pyproject.toml`, so the directory walk is exercised. It proves that red refuses a passing test, a skipped test, a syntax error, a file with no tests, and a slice mixing a pytest file with a TypeScript test; that red accepts a missing module (class `missing-module`, zero tests recorded, baseline 1, runner `pytest`, invoked as `uv run pytest` from `apps/server`) and then an assertion failure (class `assertion`); that green refuses the still-failing test by name, accepts the fixed implementation, refuses a RED test skipped through a `conftest.py` (so the locked file is byte-identical and the refusal is the skip, not R-410), and refuses a deleted baseline test; that green still refuses the failing implementation when the passing one's bytecode sits in the tree with a matching mtime and size; that `open --refactor` without uv falls back to the `.venv` interpreter with a warning, and that the JUnit converter then runs through that interpreter too; and that the runs leave the tree clean.
- The fixture fails against `origin/main`'s `tdd.sh` at its first assertion ("a passing pytest test must be refused as passing"), and it fails when `--continue-on-collection-errors` is removed from the new runner. The stale-bytecode case failed against the first commit's runner ("pytest green must run the source on disk, not a stale in-tree .pyc") and passes with the bootstrap; the converter case failed against the first commit ("the JUnit converter must run through the project's .venv python") and passes with `project_python`.
- CI failed twice on the first commit at "pytest green must pass once score returns 2", with the GREEN run executing the previous implementation, and did not reproduce on macOS or in Ubuntu 24.04 containers. After the stale-bytecode case was added, CI failed it with the environment-variable fix in place, and diagnostics printed from the fixture showed why: the runner's pytest is `/opt/pipx_bin/pytest` with the shebang `#!/opt/pipx/venvs/pytest/bin/python -E`, so the bytecode variables never reached Python, and the in-tree `score.cpython-312.pyc` was loaded. The bootstrap does not depend on the environment, and the fixture passes in an Ubuntu container whose pipx pytest shebang was edited to carry `-E`. The diagnostics were removed once they had answered the question.
- `claude/enforce/tests/run-tests.sh` and `claude/hooks/tests/run-tests.sh` pass with HOME pointed at a temporary directory whose `.claude` links to the worktree's `claude/`. `shellcheck --severity=error` is clean on `tdd.sh` and the fixture, and both translator `--check` runs are clean.

## Review

Copilot left two comments. The converter required `python3` on PATH even when the runner fell back to the project's `.venv` interpreter; fixed test-first with `project_python` and the `uv run --no-project python` fallback. This document said the converter runs under `python3` while the code also fell back to `python`; the decision entry now states the full interpreter order.

## Reflection

The task framed JUnit XML against a JSON plugin, but the decision that mattered more was the XML family: the default xunit2 output looked sufficient until mapping a test back to its file, where only the dotted class name was left. The first version of the fixture passed on its first run, which proved nothing on its own, so each load-bearing flag was removed in turn to confirm the fixture fails without it; that is how the stale-bytecode effect of `PYTHONDONTWRITEBYTECODE` surfaced, which had been added only to keep the tree clean. What I got wrong first was treating that flag as the fix: it stops bytecode writes but not reads, so a `.pyc` the developer's own run left behind could still produce a false GREEN. What I got wrong second was assuming an environment variable reaches the interpreter at all; the fixture's own diagnostics in CI showed a `-E` shebang discarding it, which is why the setting now lives in code the runner passes to the interpreter it starts. Time from starting implementation to the first version of this document was about fifteen minutes, and the review and CI rounds took about an hour more.
