# tdd.sh classifies a Vitest or Jest assertion RED by the runner's own output

Refs: IAN-161

## Summary

`enforce/tdd.sh red` accepts a failing Vitest or Jest test as the assertion RED when its failure text matches `ASSERTION`. Until now that pattern was `AssertionError|expected|toBe|toEqual|toMatch|toThrow|toHaveBeen`, and the bare word `expected` matches any plain error that says it. The IAN-160 review showed the consequence: `it("x", () => { throw new Error("timeout: expected reply"); })` was accepted as `[assertion, 1 test(s)]`, so a test that fails for a reason unrelated to the behavior under test could be locked as the slice's RED. The bare matcher names had the same weakness, since `throw new Error("toBe or not toBe")` also matched. This change restricts the pattern to the markers that Vitest and Jest themselves write when an assertion fails, so a plain error is refused as unclassified whatever its message says, while every assertion shape the two runners really produce stays the assertion RED.

## What changed

- **The pattern.** `ASSERTION` in `claude/enforce/tdd.sh` now accepts only these markers:
  - `AssertionError`, which Vitest writes for every chai matcher, `assert.*`, `expect.fail`, `expect.soft`, and `should` failure.
  - The stack frame of a Vitest wrapper that rethrows an assertion as a plain `Error`: `__VITEST_RESOLVES__`, `__VITEST_REJECTS__`, `__VITEST_POLL_CHAIN__` (`expect.poll`), and `__VITEST_EXTEND_ASSERTION__` (an `expect.extend` matcher).
  - A snapshot mismatch (``Snapshot `name 1` mismatched``), which every Vitest snapshot matcher reports.
  - Vitest's own messages for an unmet `expect.assertions(n)` and `expect.hasAssertions()`.
  - A Jest matcher hint: `expect(...)` followed by an optional `.not`, `.resolves`, or `.rejects` and a call to any matcher whose name is a JavaScript identifier, non-ASCII names included, which covers `expect(received).toBe(expected)`, the spy aliases such as `expect(jest.fn()).lastCalledWith(...expected)`, and Vitest's Jest-style `toSatisfy` hint.
  - Jest's `expect.assertions(` and `expect.hasAssertions(` hints, and jest-circus's reformatting of a `node:assert` failure as `assert.strictEqual(received, expected)` at the start of a line.
  - Not a marker: a Jest `expect.extend` matcher whose message has no `this.utils.matcherHint`. Its only trace in the report is an `Object.toX` frame at the call site, and real Jest 29 writes the same frame for a plain `Error` thrown by a helper method named `toX`, so such a matcher is refused as unclassified. A custom matcher that builds its message with `matcherHint`, as Jest's own matchers do, is accepted through the hint.
- **Colour.** `JQ_FAILURE_RESULT` strips ANSI colour codes from each failure message before it is classified. Under `FORCE_COLOR`, which jest-worker forwards, Jest splits every hint with escape codes (`expect(…received…).…toBe`), and Vitest's `toSatisfy` hint is coloured even without it.
- **Docs.** The `tdd.sh red` paragraph in `claude/enforce/README.md` lists what the assertion RED is under Vitest and Jest, and says that a plain `Error` mentioning "expected" is not one. `claude/enforce/hook-hashes.txt` is regenerated. The Codex and Cursor ports were regenerated as well and did not change, because neither carries `tdd.sh` or the enforce README.

## Architectural decisions

- **Chosen: derive the markers from real runner output.** Before each version of the pattern, throwaway projects ran the Vitest bundled in `enforce/node_modules` and an installed Jest 29.7 against every matcher family and assertion style, and the pattern was checked against each recorded `failureMessages` entry. **Alternative:** write the pattern from the runners' documentation. **Why not:** the cases that break a naive pattern are exactly the undocumented ones. `.resolves`, `.rejects`, `expect.poll`, and Vitest custom matchers rethrow as a plain `Error` that is recognizable only by a stack frame, snapshot matchers say neither `AssertionError` nor `expect(`, and jest-circus rewrites a `node:assert` failure so that it no longer says `AssertionError`.
- **Chosen: recognize Vitest's wrappers by their stack frames.** The frames `__VITEST_RESOLVES__`, `__VITEST_REJECTS__`, `__VITEST_POLL_CHAIN__`, and `__VITEST_EXTEND_ASSERTION__` are named functions in Vitest's own source, so they appear only when the failure came from that wrapper. **Alternative:** the `expected .* to ` alternative the ticket suggested. **Why not:** it still accepts `throw new Error("expected reply to arrive")`, the same kind of plain error this change exists to refuse, and the fixture checks that such an error is refused.
- **Chosen: a `.resolves` or `.rejects` that sees the wrong promise outcome is an assertion RED.** `await expect(p).resolves.toBe(1)` on a promise that rejects fails as ``promise rejected "Error: …" instead of resolving``, and `.rejects` on a promise that resolves fails as `promise resolved "1" instead of rejecting`. Both are the assertion itself failing, which is what a RED for an unwritten async unit usually looks like, so both are accepted. The first version of this branch accepted the `.resolves` case and refused the `.rejects` case, which the review flagged as inconsistent.
- **Chosen: accept any matcher name after a Jest hint, not only `to*`.** The Jest 29 spy aliases (`lastCalledWith`, `nthCalledWith`, `lastReturnedWith`, `nthReturnedWith`) and custom matchers written with `matcherHint` do not start with `to`. The hint's `expect(…).name(` shape is specific enough on its own.
- **Chosen: strip colour instead of forcing it off.** Setting `NO_COLOR` or `FORCE_COLOR=0` on the runner would also work, but the environment a project's test script sets can override it, and stripping at the one point where failures are read covers every runner and setting.
- **Accepted residual.** A plain error whose message contains a marker verbatim, such as `throw new Error("call expect(x).toBe(y) first")` or `throw new Error("__VITEST_RESOLVES__")`, is still accepted. Neither occurs by accident, and refusing them would need the error's type, which the JSON reports do not carry apart from the message text.

## Testing

- `claude/enforce/tests/tdd-red-green.test.sh` gains a section against the real bundled Vitest. It opens a slice and checks that `red` refuses three plain errors as unclassified (`timeout: expected reply`, `expected reply to arrive`, and `toBe or not toBe`) and leaves the phase `open`. It then checks that twelve real assertion failures are each accepted with failure class `assertion`: `toBe`, `toHaveBeenCalled` on `vi.fn()`, `assert.equal`, `.resolves.toBe`, `expect.assertions(1)`, `expect.hasAssertions()`, `.rejects.toThrow` with the wrong message, `.rejects` on a resolved promise, `expect.poll`, an `expect.extend` matcher, an inline snapshot mismatch, and `toSatisfy`, whose hint is coloured.
- The Jest stub in the same fixture gains ten modes, whose messages are copied from real Jest 29.7 output. `plain` (`Error: timeout: expected reply`) must be refused as unclassified by its test id. `mock`, `assertions`, `alias` (`lastCalledWith`), `nodeassert` (the jest-circus `assert.strictEqual(received, expected)` form), `colour` (a `toBe` hint split by ANSI codes), `identhint` (a hint for a matcher named `toBe_close2`), and `unicodehint` (a hint for `toBeé`) must each be the assertion RED. `custom` (a hint-less `expect.extend` message with its `Object.toBeWithinRange` frame) and `helper` (a plain `Error: boom` thrown by a helper method with the same frame) must each be refused as unclassified.
- RED, first round: with the first cases in place and `tdd.sh` unchanged, the fixture failed at `FAIL: a plain error is not an assertion RED: throw new Error("timeout: expected reply");`. RED, review round: with the review's cases added to the first fix, it failed at `.rejects.toThrow("other")`, refused as unclassified. It passes on the final pattern.
- Outside the fixture, the final pattern was applied to every failing test in the captured real Vitest and Jest reports. Every assertion failure was accepted, and the five plain errors (`timeout: expected reply` under both runners, a plain error from a helper, a plain error inside `vi.waitFor`, and a plain error in a test that also calls `expect.assertions`) were refused. The two contrived messages under Accepted residual were accepted, as that section says.
- `claude/enforce/tests/run-tests.sh` and `claude/hooks/tests/run-tests.sh` pass, run with HOME pointed at a temporary directory whose `.claude` links to the worktree's `claude/`. `node translate/codex.mjs --check` and `node translate/cursor.mjs --check` exit 0.
- **The RED was proved by running the fixture directly, not by `tdd.sh red`.** `tdd.sh red claude/enforce/tests/tdd-red-green.test.sh` cannot accept a RED in this fixture for two reasons. `fixture-implementation-root.test.sh` runs `tdd-red-green.test.sh` itself, so it goes red together with the fixture. And `enforce/hook-hashes.txt` hashes every `enforce/tests/*.sh`, so editing the test makes `hook-hashes-closure.test.sh` report drift until the hashes are regenerated, which is a production write the open lock denies. The empty slice was closed from `open` and the RED was recorded by hand. That gap is filed as IAN-162.

## Codex review

Codex was out of quota (its CLI reported the usage limit until 2026-09-21), so the pre-merge review ran as a separate Claude agent on fable, given the diff and the acceptance criteria but not my reasoning. It verified each finding against real Vitest 5.0 and Jest 29.7 output and reported eleven:

- HIGH, fixed: Vitest snapshot matchers fail as ``Snapshot `x 1` mismatched`` and were lost. The snapshot message is now a marker.
- HIGH, fixed: Vitest `.rejects` with a failing matcher (`__VITEST_REJECTS__`) was lost. The wrapper frames are now markers.
- HIGH, fixed: `node:assert` under Jest is reformatted as `assert.strictEqual(received, expected)` and was lost. That line shape is now a marker.
- HIGH, fixed for Vitest, refused for Jest: `expect.extend` matchers in both runners were lost. Vitest's `__VITEST_EXTEND_ASSERTION__` frame is now a marker. Jest's `Object.toX` frame was a marker until Copilot's third round showed that it also accepts a helper's plain error, so a Jest custom matcher now needs a hint (see Copilot review).
- MEDIUM, fixed: `expect.poll` (`__VITEST_POLL_CHAIN__`) was lost.
- MEDIUM, fixed: the Jest 29 spy aliases (`lastCalledWith` and the others) were lost. The hint now accepts any matcher name.
- MEDIUM, fixed: under `FORCE_COLOR`, ANSI codes split every Jest hint. Colour is now stripped before classification.
- MEDIUM, fixed: `.resolves` on a rejected promise was accepted while `.rejects` on a resolved one was refused. Both are now accepted, as described under Architectural decisions.
- LOW, fixed: the pattern comment, the README, and the fixture header overstated what the first version covered. All three are rewritten, and the fixture now covers each lost shape.
- LOW, accepted: a plain error whose message contains a marker verbatim is still accepted. See the accepted residual above.
- LOW, no change: the pattern is plain POSIX ERE with no BSD and GNU divergence. `[A-Z]` also matches lowercase under BSD grep in a single-byte locale, which only widens a stack-frame match.

## Copilot review

Copilot's first round left one inline finding. The matcher name after a Jest hint and in the `Object.toX` frame was limited to letters, so a custom matcher named with digits or `_` (`toBeWithinRange2`) was refused. Both fragments now accept any JavaScript identifier, and two Jest-stub modes cover a hint and a frame with such a name; the hint case failed first, as expected. Its summary also mentioned two documentation statements that needed qualification without naming them; the one statement that was affected, "any matcher call", now says the name must be a JavaScript identifier.

Copilot's second round confirmed the fix and raised two more points without inline threads. A Jest frame-only matcher whose name continues in lowercase after `to` (`tobeWithinRange`) was still refused, so the frame now accepts any identifier characters after `to`, with a Jest-stub case that failed first. The README said a plain `Error` naming a matcher is never accepted, which contradicts the accepted residual, so it now says such an error is refused unless it quotes a marker verbatim.

Copilot's third round found that the `Object.toX` frame marker was not exclusive to `expect.extend`: a helper method `const helper = { toBeWithinRange() { throw new Error("boom"); } }` produces the same frame, so a plain error locked as an assertion RED, which is the failure this PR exists to prevent. Real Jest 29 output confirmed there is nothing else in the report to tell the two apart, since `JestAssertionError` is reported as `Error:` and the stack is rewritten to the call site. The frame marker is removed, with the user's agreement, so a Jest custom matcher RED now needs `this.utils.matcherHint` in its message; a `helper` Jest-stub case failed first and the `custom` case now expects a refusal. The two frame-only cases from round two are dropped, since the shape they covered is now refused.

Copilot's fourth round noted that the matcher name after a Jest hint was limited to ASCII identifier characters, so a valid matcher such as `toBeé` was refused. The name is now any run of characters other than whitespace, `.`, and parentheses, which covers every JavaScript identifier without spelling out Unicode classes that BSD and GNU grep treat differently; a `unicodehint` Jest-stub case failed first.

## Reflection

I first read the bug as a one-word deletion, dropping `expected` and keeping the rest. Running the real Vitest showed that this would silently turn legitimate REDs into refusals, and my first version still lost more than I had checked for. I had probed about twenty matcher styles in one runner, and the review found snapshot matchers, `.rejects`, `expect.poll`, custom matchers, the Jest spy aliases, jest-circus's `node:assert` reformatting, and coloured output. What I understand now is that "the assertion markers" of a runner are not one string. They are a set of wrapper shapes, and the bare word `expected` had been covering all of them by accident. The worktree was also first cut before IAN-160 (#81) merged, so the test edit had to be rebased onto that PR's Jest stub before the RED run meant anything. Time from the first RED run to the first version of this document was about fifteen minutes, and the review round took about forty more.
