# tdd.sh classifies a Vitest or Jest assertion RED by the runner's own output

Refs: IAN-161

## Summary

`enforce/tdd.sh red` accepts a failing Vitest or Jest test as the assertion RED when its failure text matches `ASSERTION`. Until now that pattern was `AssertionError|expected|toBe|toEqual|toMatch|toThrow|toHaveBeen`, and the bare word `expected` matches any plain error that says it. The IAN-160 review showed the consequence: `it("x", () => { throw new Error("timeout: expected reply"); })` was accepted as `[assertion, 1 test(s)]`, so a test that fails for a reason unrelated to the behavior under test could be locked as the slice's RED. The bare matcher names had the same weakness, since `throw new Error("toBe or not toBe")` also matched. This change restricts the pattern to the markers that Vitest and Jest themselves write when an assertion fails, so a plain error is refused as unclassified whatever its message says.

## What changed

- **The pattern.** `ASSERTION` in `claude/enforce/tdd.sh` is now `AssertionError`, a Jest matcher hint (`expect(...)` followed by an optional `.not`, `.resolves`, or `.rejects` and a `.toX` matcher, which covers `expect(received).toBe(expected)` and `expect(jest.fn()).toHaveBeenCalled()`), Jest's `expect.assertions(` and `expect.hasAssertions(` hints, Vitest's `__VITEST_RESOLVES__` stack frame, and Vitest's two messages for `expect.assertions` and `expect.hasAssertions`. A comment above the pattern says which runner writes each marker. The pytest and bash-fixture patterns are unchanged.
- **Docs.** The `tdd.sh red` paragraph in `claude/enforce/README.md` now says what the assertion RED is under Vitest and Jest, and that a plain `Error` mentioning "expected" is not one. `claude/enforce/hook-hashes.txt` is regenerated. The Codex and Cursor ports were regenerated too, and neither changed, because neither carries `tdd.sh` or the enforce README.

## Architectural decisions

- **Chosen: derive the markers from real Vitest output.** Before writing the pattern, a throwaway project ran the Vitest bundled in `enforce/node_modules` against more than twenty matchers and assertion styles and recorded each `failureMessages` entry. Every matcher, `assert.*`, `expect.fail`, and `expect.soft` failure starts with `AssertionError:`. Three do not. `.resolves` rethrows the inner failure as a plain `Error: expected 1 to be 2`, identifiable only by its `__VITEST_RESOLVES__` stack frame. `expect.assertions(n)` fails with `Error: expected number of assertions to be n, but got m`, and `expect.hasAssertions()` fails with `Error: expected any number of assertion, but got none`. The old pattern accepted all three through the bare word `expected`, so each needs its own marker to avoid losing it. **Alternative:** guess the markers from documentation. **Why not:** the `.resolves` case would have been missed, and it is a common RED shape for async code.
- **Chosen: leave out the `expected .* to ` alternative the ticket suggested.** Every Vitest message of that shape already carries `AssertionError`, except the three cases above, which have narrower markers. The broader alternative would still accept `throw new Error("expected reply to arrive")`, a plain error of the same kind this change exists to refuse, and the fixture checks that it is refused.
- **Chosen: match Jest by its matcher hint rather than the bare matcher names.** Jest heads every assertion failure with a hint such as `expect(received).toBe(expected)`. Matching the hint keeps every Jest case the old matcher names accepted, including `expect(jest.fn()).toHaveBeenCalled()`, while a message that merely contains `toBe` no longer counts. The `expect.assertions(`/`expect.hasAssertions(` hint is a small addition, since the old pattern did not accept Jest's `expect.assertions` failure (its body says `Expected one assertion`, with a capital E), but it is Jest's own assertion output and belongs in the same class.
- **Not changed: `.rejects` under Vitest.** Vitest reports an unmet `.rejects` as `Error: promise resolved "1" instead of rejecting`, which the old pattern did not accept either. Accepting it would widen the RED class rather than tighten it, so it is left for a separate decision.

## Testing

- `claude/enforce/tests/tdd-red-green.test.sh` gains a section against the real bundled Vitest. It opens a slice and checks that `red` refuses three plain errors as unclassified (`timeout: expected reply`, `expected reply to arrive`, and `toBe or not toBe`) and leaves the phase `open`. It then checks that six real assertion failures are each accepted with failure class `assertion`: `toBe`, `toHaveBeenCalled` on `vi.fn()`, `assert.equal`, `.resolves.toBe`, `expect.assertions(1)`, and `expect.hasAssertions()`.
- The Jest stub in the same fixture gains three modes. `plain` (`Error: timeout: expected reply`) must be refused as unclassified by its test id. `mock` (`expect(jest.fn()).toHaveBeenCalledWith(...expected)`) and `assertions` (`expect.assertions(1)`) must each be the assertion RED.
- RED: with the new cases in place and `tdd.sh` unchanged, the fixture failed at its first new assertion, `FAIL: a plain error is not an assertion RED: throw new Error("timeout: expected reply");`. With the new pattern it passes.
- `claude/enforce/tests/run-tests.sh` and `claude/hooks/tests/run-tests.sh` were run with HOME pointed at a temporary directory whose `.claude` links to the worktree's `claude/`; results are in the PR body.
- **The RED was proved by running the fixture directly, not by `tdd.sh red`.** `tdd.sh red claude/enforce/tests/tdd-red-green.test.sh` cannot accept a RED in this fixture for two reasons. `fixture-implementation-root.test.sh` runs `tdd-red-green.test.sh` itself, so it goes red together with the fixture. And `enforce/hook-hashes.txt` hashes every `enforce/tests/*.sh`, so editing the test makes `hook-hashes-closure.test.sh` report drift until the hashes are regenerated, which is a production write the open lock denies. The empty slice was closed from `open` and the RED was recorded by hand. That gap is filed as IAN-162.

## Reflection

I first read the bug as a one-word deletion: drop `expected` and keep the rest. Running the real Vitest showed that deleting it would have silently turned three legitimate REDs (`.resolves`, `expect.assertions`, `expect.hasAssertions`) into refusals, because those are the Vitest failures that do not say `AssertionError`. The bare matcher names turned out to be the same kind of bug as `expected`, just less likely to trigger. The part I got wrong first was the base: the worktree was cut before IAN-160 (#81) merged, so the test edit conflicted with that PR's new Jest stub mode and had to be rebased before the RED run meant anything. Time from the RED run to the first version of this document was about fifteen minutes.
